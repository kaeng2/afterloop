> **가장 중요한 규칙**
> 1. **화면은 계산하지 않는다.** 기대 손실·확률·금액·점수는 `src/engine/` 결과를 옮기기만 한다. 화면 코드에 `+ - * /`로 돈이나 점수를 만드는 곳이 없어야 한다.
> 2. **이 화면은 PayPal에 POST를 한 번도 보내지 않는다.** [Run autopilot]은 조회(GET)와 판정만 한다. 분쟁에 대한 자동 실행은 없다 (SPEC 6장).
> 3. PayPal·LLM 호출은 서버 코드에서만 한다. 비밀값이 브라우저 묶음에 들어가면 안 된다.
> 4. `.env`를 찾거나 만들지 않는다. 실제 PayPal·LLM 호출을 하지 않는다 (가짜 클라이언트로만 시험한다. 실제 조회 확인은 병합 뒤 컨트롤 타워가 한다).

## 이 작업이 만드는 공용 뼈대 (나머지 화면 지시서는 읽기만 한다)

화면은 5개이고 ui 레인 worktree는 하나다. 그래서 **한 번에 하나씩** 만든다.

**제안 순서: T012a (공용 뼈대, 1시간) → T009 (S5) → T013 (S2) → T012b (S4 Inbox) → T016 (S3) → T014 (S1).**
- 화면 순서는 1차 심사위원 리뷰 권장(S5 → S2 → S4 → S3 → S1, 영상 초 수가 큰 순서)을 그대로 따른다.
- 리뷰와 다른 점은 하나다: 공용 뼈대(아래 표의 **T012** 칸 중 `src/app/inbox/`를 뺀 것)를 맨 앞에 따로 둔다. 이유: S5와 S4가 같은 "실제 분쟁 읽기" 서버 함수와 배지·문구 읽기를 쓴다. S5 지시서(T009)는 이미 가장 크다. 뼈대를 T009에 넣으면 대표 장면 작업이 더 커지고, 두 화면이 같은 파일을 고치게 된다.
- 사람이 T012를 나누지 않기로 하면: T012 전체 → T009 → T013 → T016 → T014 (S4가 S5보다 먼저가 된다. 리뷰 권장과 달라지는 이유는 위와 같다).

## 화면에 보여 줄 것
왼쪽 표 (AG Grid Community), 오른쪽 패널 (오토파일럿).

| 항목 | 무엇을 | 어디서 가져오는지 |
|---|---|---|
| Risk | 점수와 구간 배지 (Low / Watch / High) | `escalationRisk(signals).score`·`band`. 신호가 없으면 빈칸 (선행 나·다) |
| Buyer | 이름 | `seedBuyers`의 `name` (연결 표: 선행 라). 문의 행은 `SeedInquiry.buyerId` |
| Language | KO / EN / JA / DE | `seedBuyers`의 `language` |
| Type | 세부 유형 칩 (예: B1) + 확신도가 낮으면 "Check type" 배지 | `board.cause.subtype`, `board.cause.needsReview`. 문의 행은 `SeedInquiry.signal` |
| Amount | 분쟁 금액 | `board.amountCents` → `centsToDisplay` |
| Due | 응답 기한. 없으면 "No deadline" (문구 파일) | `board.dueDate` (빈 문자열 = 기한 없음. 날짜를 지어내지 않는다) |
| Suggested | 추천 수와 기대 손실 | `recommend(board).best` → `move`(문구 `move.fight` 등), `expectedLossCents`. `best`가 없으면 `board.directHandling` 문구 |
| Status | PayPal 상태 | 분쟁 상세의 `status` (예: `WAITING_FOR_SELLER_RESPONSE`, `UNDER_REVIEW`)를 문구 키로 바꿔 표시. D3(Mike)는 PayPal 심사 중으로 보인다 |
| 배지 | 'Demo data', 'Assumption', 'AI suggests', 'Code decides' | 아래 "배지" |
| 행 클릭 | 분쟁 행 → `/cases/<disputeId>` | — |
| 오토파일럿 규칙 3줄 | 고정 문구 | `config/copy.en.json` `inbox.rule.*` (원문 8장 S4의 세 문장) |
| [Run autopilot] | 서버에서 목록 조회 → 판정 → 로그 | 아래 "누르면" |
| 로그 한 줄 | 시각 · 대상 · 판정 · 규칙 이름 | `recommend(board).autopilot.reason` (엔진이 만든 영어 문장 그대로) + `autopilot.rule` + `autopilot.verdict`. 시각은 누른 시각 |
| 안내 한 줄 | "New disputes can take a few minutes to appear in PayPal's list." | 문구 파일. 방금 접수된 분쟁은 목록에 늦게 나온다 (SPEC 9-4) |

- 행 = 실제 분쟁(시연 제외를 뺀 것) + 시드 문의. 종결된 시드 분쟁(D4~D9)은 이 표에 넣지 않는다.
- 기본 정렬 = 확대 위험 높은 순. 점수가 없는 행은 맨 뒤.
- AG Grid는 Community 기능만: 정렬, 텍스트 필터, 셀 렌더러, 행 클릭. 행 그룹·set filter·통합 차트·`ag-grid-enterprise`는 쓰지 않는다.

### 배지
- 'Demo data': 시드 문의 행 전체. 실제 분쟁에 덧씌운 시드 값 — D2의 배송사 추적·통관 이벤트와 그 결과(A2), D3의 "이전 미수령 2건"과 배송 완료 기록, 서연의 무응답 신호 (SPEC 10장 ①②③).
- 'Assumption': 기대 손실 (가정값 `config/params.json`에서 나온 수).
- 'AI suggests'(보라) / 'Code decides'(회색): `cause.source`가 `llm`이면 AI, `rule`이면 Code. 추천·점수·오토파일럿 판정은 항상 Code.
- AI를 못 쓰면 "AI unavailable — showing rules only" (SPEC 3장).

### [Run autopilot]을 누르면 (서버)
1. `listDisputes` → 시연 제외 ID를 뺀다 → 연결 표에 있는데 목록에 없는 분쟁은 `getDispute`로 직접 읽는다 (목록 지연).
2. 건마다 `getDispute` → `toClassifyInput` → `classifyDispute` → `toBoardState` → `recommend`.
3. 이전 미수령 분쟁 수는 **시연 제외 분쟁을 뺀 목록**으로 `countPriorInrDisputes`를 부른다 (안 빼면 서연이 1로 나온다).
4. 화면에는 `BoardState`와 판정만 보낸다. 구매자 이메일·주소·`payer_id`·응답 원문은 브라우저로 보내지 않는다.
5. POST는 없다. 돈이 움직이는 수는 "Waiting for your approval"로만 보인다 (실행 버튼은 이 화면에 두지 않는다).

## 보기용 데이터를 만드는 순수 함수 (`src/app/inbox/model.ts`)
DOM·네트워크·시계·난수를 쓰지 않는다. 시각은 인자로 받는다. 인수 테스트(AC19)가 이 함수를 직접 부른다.

- `buildInboxRows(input, params?, rules?)` → 행 배열. `input`: 분쟁마다 `{ board, buyer, statusCode, signals | null, demoFields }`, 문의 배열, 구매자 배열. 안에서 `recommend(board, params, rules)`와 `escalationRisk(signals, rules)`를 **그대로 불러** 결과를 옮긴다.
- `buildAutopilotLog(rows, nowIso)` → 로그 줄 배열 (`reason`·`rule`·`verdict`는 엔진 값 그대로).
- `sortByRisk(rows)` → 정렬된 새 배열.
- 공용 (`src/app/_shared/`): `t(key, params?)` — 문구 파일에서 읽고 `{{이름}}`을 채운다. 없는 키면 예외. `withoutDemoExcluded(disputes, links)` — 시연 제외를 뺀다.
