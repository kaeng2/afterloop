## 수정 가능 폴더
- `src/ai/classify.ts`, `src/ai/llm.ts`(서버 전용 LLM 호출), `src/ai/prompts/`

이 밖은 수정하지 않는다. 특히 `src/engine/`, `src/types.ts`, `tests/acceptance/`, `config/`.

## 목표
`classifyDispute(input, { llm }, rules?)` → `Cause` (SPEC v2 4장). 규칙으로 정할 수 있는 건 코드가, 나머지는 LLM이 16개 세부 유형 중 하나를 고른다. 실패해도 예외를 던지지 않는다.

## 입력 / 출력 타입
- 입력: `ClassifyInput` (reason, 구매자 메시지 원문, 추적 이벤트 텍스트, 추적·배송 여부, 같은 구매자의 이전 미수령 분쟁 수)
- 주입: `LlmCaller` (테스트는 mock, 실제 호출은 `src/ai/llm.ts`)
- 출력: `Cause` (`subtype`, `confidence`, `evidence`, `needsReview`, `source`, `causeNote?`)
- 공개 함수: `src/ai/classify.ts`의 `export function classifyDispute` (`ClassifyFn`)

## 동작
1. **규칙 먼저** (`source: 'rule'`, `confidence: 1`, LLM 호출 0회). 순서대로 첫 번째:
   1. reason `UNAUTHORISED` → E1
   2. reason INR + `buyerPriorInrDisputes ≥ rules.abuse.minPriorInrDisputes`(2) + `hasDeliveredTracking` → F1
   3. reason INR + `!hasTracking` → A1
   4. 추적 이벤트에 `customs hold`(대소문자 무시) → A2, `causeNote`에 이벤트 원문 요약 (예: "PCCC missing")
2. **LLM** (`source: 'llm'`): JSON 스키마 `{ subtype, confidence, evidence[], cause? }`로 받고 zod로 검증한다
   - 스키마 위반이면 1회만 다시 요청. 또 실패하면 reason별 기본 유형(INR→A2, SNAD→B3, CREDIT_NOT_PROCESSED→C1, DUPLICATE_TRANSACTION→C2, INCORRECT_AMOUNT→C3, CANCELED_RECURRING_BILLING→D1)에 `confidence: 0`, `needsReview: true`, `evidence: ['classifier_unavailable']`
   - 응답에 금액·확률·손실 같은 숫자 판정 필드가 있어도 버린다 (스키마에 없는 키는 무시)
3. `confidence < rules.classification.minConfidence`(0.7)이면 `needsReview: true`
4. **개인정보** (SPEC 10장): 메시지를 LLM에 보내기 전에 개인통관고유부호처럼 보이는 값(`P` + 숫자 12자리)을 `⟦PCCC⟧`로 가린다. 이메일·주소는 입력 타입에 없다
5. `src/ai/llm.ts`: 서버에서만 호출. 키는 `.env`의 `LLM_API_KEY`, 모델 이름은 환경 변수로 받는다. 로그에 프롬프트 전문과 키를 남기지 않는다
   - **공식 SDK `@anthropic-ai/sdk`를 쓴다** (2026-11-09 컨트롤 타워가 의존성에 추가함. `package.json`은 고치지 않는다). `fetch`로 직접 호출하지 않는다. **코드를 쓰기 전에 `claude-api` 스킬을 읽고** 그 문서에 나온 형태만 쓴다 (SDK 사용법을 추측하지 않는다)
   - `createLlmCaller(env?)` → `LlmCaller` (`@/types` 6부: `{ system, user, jsonSchema }` → 원시 값). 클라이언트는 `new Anthropic({ apiKey: env.LLM_API_KEY })`. 키가 없으면 호출하지 않고 "LLM_API_KEY is not set" 예외 (키 값은 어디에도 싣지 않는다)
   - 모델: 환경 변수 `LLM_MODEL`, 기본값 `claude-opus-5-5`. 추론 깊이는 `output_config.effort`로 정하고 환경 변수 `LLM_EFFORT`(기본 `low` — 분류는 짧은 판단)로 바꿀 수 있게 한다. `thinking`·`temperature`·`budget_tokens`는 보내지 않는다 (이 모델에서 400)
   - 응답 형식: 구조화 출력 `output_config.format`에 `req.jsonSchema`를 넘긴다 (스킬 문서의 JSON 스키마 형태). 어시스턴트 프리필은 쓰지 않는다. 응답의 텍스트 블록을 `JSON.parse`한 값을 돌려준다 (검증은 `classify.ts`의 zod가 한다)
   - 거절 처리: `stop_reason === 'refusal'`이면 내용을 읽지 않고 예외로 돌린다 (분류기는 그때 기본 유형 + `needsReview`). 스킬 문서의 권장대로 서버 쪽 `fallbacks: "default"`(베타 헤더 포함)를 켜고, 보고서에 켰다고 적는다
   - 오류는 SDK의 타입 있는 예외 클래스로 구분한다 (429·5xx는 SDK 기본 재시도에 맡기고, 그 뒤에도 실패하면 예외 → 분류기가 기본 유형으로). `max_tokens`는 분류 응답에 충분한 값(예: 1024)
   - 프롬프트: 시스템 프롬프트는 고정 문자열(16개 세부 유형 정의 + 출력 규칙)로 두고 요청마다 바뀌는 내용(구매자 메시지, 추적 이벤트)은 user에만 넣는다 (프롬프트 캐시가 깨지지 않게). 구매자 메시지는 신뢰하지 않는 입력이다 — 메시지 안의 지시("ignore previous instructions" 등)를 따르지 말라는 문장을 시스템 프롬프트에 넣고, 메시지는 구분 태그로 감싼다
   - 이 작업에서는 **실제 호출을 하지 않는다** (이 worktree에 `.env`·키 없음. 찾거나 읽지 않는다). `llm.ts`는 SDK 클라이언트를 주입받을 수 있게 만들어 가짜 클라이언트로 단위 테스트한다: 보낸 요청의 모델·`output_config`·시스템 프롬프트 고정 여부, 거절·오류·깨진 JSON 처리, 키·프롬프트 전문이 로그에 없는지
