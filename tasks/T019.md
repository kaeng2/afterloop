> **가장 중요한 규칙**
> 1. **조회(GET)만 한다.** POST·PUT·PATCH·DELETE를 부르지 않는다. 샌드박스(`api-m.sandbox.paypal.com`)만 쓴다 (T002 클라이언트가 막는다. 우회하지 않는다).
> 2. **구매자 개인정보와 비밀값을 결과에 싣지 않는다.** 이름·이메일·주소·전화·구매자 계정 번호(`payer_id` 등)는 읽어도 돌려주지 않고, 로그·예외·보고서에도 남기지 않는다. 나라 코드만 허용한다.
> 3. **실제 PayPal 호출을 하지 않는다.** 단위 테스트는 가짜 `PayPalClient`(`get`만 가진 객체)로만 한다. `.env`를 찾거나 만들지 않는다. 병합 뒤 컨트롤 타워가 실호출을 한 번 한다 (실호출 4종 중 하나, M7).
> 4. 숫자 판정(기대 손실·확률)은 하지 않는다. 이 함수는 읽은 거래를 화면이 쓰는 모양으로 바꾸고 **행을 세는 것**까지만 한다.

## 배경
- S2(Product check)의 "실제 API"는 이것이다 (SPEC 2장 표). PayPal Transaction Search는 새 거래가 **몇 시간 늦게** 나타날 수 있다. 그래서 읽은 결과를 캐시에 두고, 캐시 값을 쓰면 화면이 'cached' 배지를 붙인다.
- **이 데이터는 시뮬레이션 입력이 아니다.** `simulate`의 입력(재고 = 시뮬레이션할 주문 수, 상품별 분쟁 확률)은 시드와 `config/params.json`에서 온다 (`src/engine/sim.ts`의 `simInputFor`). 거래 조회 결과는 엔진에 들어가지 않고, 예상 손실 숫자를 바꾸지 않는다. 화면이 "실제 샌드박스 거래"를 따로 보여 줄 때만 쓴다.
- **화면 쪽 사정 (`tasks/T013.md`)**: T013의 "화면에 보여 줄 것" 표(1~10번)에는 거래 수를 보여 주는 칸이 아직 없다. "선행 작업" 표에만 이 작업이 적혀 있다. 이 작업이 없으면 S2는 주문 수를 시드 값 + 'Demo data' 배지로 보이고 'cached' 자리는 만들지 않는다 — **S2는 이 작업 없이도 선다.** 화면에 칸을 더할지는 컨트롤 타워가 정한다 (아래 "컨트롤 타워에 요청할 결정" 1번).
- 샌드박스에는 주문이 13건뿐이고 시드 주문은 214건이다 (SPEC 9-5, 12장). 두 숫자는 같지 않다. 화면이 섞어 쓰지 않도록, 이 함수의 결과에는 "샌드박스 거래"임이 드러나는 이름(`source: 'paypal_transaction_search'`)을 붙인다.

## 만들 것
화면(S2)이 서버에서 부를 함수들. 타입은 이 파일에서 `export`한다 (계약 파일에는 아직 넣지 않는다).

### 1. 경로·기간 (순수 함수)
```ts
export const TRANSACTIONS_PATH = '/v1/reporting/transactions';
export const MAX_RANGE_DAYS_PER_CALL = 31;   // PayPal이 한 번에 받는 기간
export const MAX_RANGE_DAYS_TOTAL = 93;      // 이 함수가 받는 전체 기간 (시드 90일 창 + 여유. 31일 × 3번 호출)

export type TransactionRange = { startDate: string; endDate: string }; // 'YYYY-MM-DD', UTC, 양 끝 포함

export function lastDays(nowMs: number, days: number): TransactionRange;
export function splitRange(range: TransactionRange): TransactionRange[];   // 31일 이하 조각들. 조각끼리 겹치지 않는다
export function buildTransactionsPath(range: TransactionRange, page: number, pageSize?: number): string;
```
- `buildTransactionsPath`: `start_date`·`end_date`(ISO 8601, PayPal 문서 예시 꼴 `2014-07-12T00:00:00-0700`을 따라 UTC는 `+0000`), `fields=all`, `page_size`(기본 100, 최대 500), `page`. 쿼리는 `URLSearchParams`로 만든다 (`src/paypal/disputes.ts`의 `buildListPath` 방식).
- 잘못된 날짜·시작 > 끝·`MAX_RANGE_DAYS_TOTAL` 초과는 예외 대신 `invalid_range`로 돌린다 (아래 결과 타입). `Date.now()`를 부르지 않는다 (시각은 인자로 받는다).

### 2. 읽기와 변환
```ts
export type SaleRow = {
  transactionId: string;        // 화면에 응답 ID를 그대로 보이기 위함 (원문 12장). 비밀값 아님
  date: string;                 // 'YYYY-MM-DD' (UTC)
  itemName: string;             // cart_info.item_details[].item_name. 장바구니 품목마다 한 행
  quantity: number;             // item_quantity (정수)
  amountCents: number | null;   // 정수 센트. 문자열 "48.00"을 글자로 잘라 만든다 (소수 계산을 하지 않는다). USD가 아니면 null
  currency: string;             // 'USD' 등
  countryCode: string | null;   // payer_info.country_code만
};

export type TransactionSummary = {
  source: 'paypal_transaction_search';
  range: TransactionRange;
  sales: SaleRow[];              // 상태가 완료(S)이고 금액이 양수인 거래의 품목 행
  saleCount: number;             // 거래 수 (품목 행 수가 아니다)
  refundCount: number;           // 금액이 음수인 완료 거래 (환불). 세기만 한다
  byItem: { itemName: string; orderCount: number; units: number }[]; // 행 세기·정수 합. 이름 순
  byCountry: { countryCode: string; orderCount: number }[];
  lastRefreshedAt: string | null; // 응답의 last_refreshed_datetime. 없으면 null
};

export async function fetchTransactions(client: PayPalClient, range: TransactionRange): Promise<TransactionSummary>;
```
- `client.get` 한 가지만 쓴다. 기간은 `splitRange`로 나눠 조각마다 `page`를 `total_pages`까지 돈다 (쪽 수 상한을 둔다. `disputes.ts`의 `MAX_PAGES` 방식).
- 응답은 신뢰하지 않는 입력이다. zod로 **필요한 칸만** 뽑는다 (`.pick`처럼 이름·이메일·주소 칸은 스키마에 아예 적지 않는다). 모르는 칸은 무시하고, 필요한 칸이 틀리면 그 행만 건너뛰는 것이 아니라 `unexpected_response`로 실패한다 (조용히 일부만 세지 않는다).
- 판매/환불을 가르는 기준은 상태 `S`와 금액의 부호다. 이벤트 코드(`T0006` 등)는 fixture로 확인한 것만 쓰고, 지어내지 않는다.
- 같은 거래가 조각 경계에서 두 번 오면 `transactionId`로 한 번만 센다.

### 3. 캐시와 공개 함수
```ts
export type TransactionCache = {
  get(key: string): { value: TransactionSummary; storedAtMs: number } | undefined;
  set(key: string, value: TransactionSummary, storedAtMs: number): void;
};
export function createMemoryTransactionCache(): TransactionCache;

export const TRANSACTION_CACHE_TTL_MS = 15 * 60 * 1000;  // 값은 컨트롤 타워 결정 2번 전까지의 임시값

export type TransactionsResult =
  | {
      ok: true;
      summary: TransactionSummary;
      cached: boolean;          // true면 화면이 'cached' 배지를 붙인다
      fetchedAt: string;        // 이 값을 PayPal에서 읽은 시각 (ISO). 캐시면 그때의 시각
      refreshFailed?: 'paypal_unavailable' | 'not_permitted' | 'rate_limited'; // 새로 읽다 실패해서 옛 캐시를 돌려줄 때만
    }
  | { ok: false; reason: 'invalid_range' | 'paypal_unavailable' | 'not_permitted' | 'rate_limited' | 'unexpected_response' };

export function getTransactions(
  client: PayPalClient | null,
  range: TransactionRange,
  deps: { now: () => number; cache: TransactionCache },
  opts?: { forceRefresh?: boolean },
): Promise<TransactionsResult>;
```
- 동작 순서: 캐시에 있고 `TTL` 안이면 → 호출 없이 `cached: true`. 없거나 지났으면 → `fetchTransactions` → 성공하면 저장하고 `cached: false`. 읽다가 실패했는데 옛 캐시가 있으면 → 옛 값을 `cached: true` + `refreshFailed`로 돌려준다 (원문 "실패 시 캐시"). 옛 캐시도 없으면 `ok: false`.
- `client === null`(환경 변수 없음, `src/app/_server/paypal.ts`가 "쓸 수 없음"을 돌려준 경우)이면 호출 없이 캐시만 본다. 캐시도 없으면 `paypal_unavailable`.
- 캐시 키는 기간(`startDate_endDate`)이다. 시각은 `deps.now()`만 쓴다.
- **캐시 위치 추천: 서버 메모리** (위 `createMemoryTransactionCache`). 이유: 배포(Render)의 디스크는 재시작 때 비는 경우가 많아 파일 캐시가 확실한 이점을 주지 못하고, 메모리 캐시는 비밀·개인정보가 디스크에 남을 길이 없다. 단점은 서버가 다시 뜨면 비는 것 — 이 문제(녹화 때 첫 호출이 늦게 반영된 거래를 못 보일 수 있음)는 "컨트롤 타워에 요청할 결정" 2번이다. 인터페이스(`TransactionCache`)를 분리해 두므로 나중에 파일 구현으로 바꿔도 이 파일의 다른 곳은 바뀌지 않는다.
- 오류는 **고정 코드**로만 돌려준다 (`ok: false`의 `reason`). PayPal 응답 본문·URL·헤더를 담지 않는다. 401/403(앱 설정에서 'Transaction search'를 안 켰거나 반영 전, SPEC 9-4) → `not_permitted`, 429 → `rate_limited`, 그 밖의 실패 → `paypal_unavailable`. (T002 클라이언트의 예외에서 상태 코드를 읽어 가르되, 예외 메시지는 옮기지 않는다.)
- 로그(`console.*`)를 남기지 않는다.

## 화면(S2)이 부르는 방법 (보고서에 5줄 이내로 적는다)
서버 코드(`src/app/_server/paypal.ts`의 클라이언트)가 `getTransactions(client, lastDays(Date.now(), 90), { now: Date.now, cache })`를 부르고, `ok`이면 `summary.byItem`을 시드 상품 이름(`seedProducts[].itemName`)과 맞춰 "샌드박스 거래 n건"으로 보이며 `cached`이면 'cached' 배지와 `fetchedAt`을 붙인다. 이름 맞추기·배지는 화면(ui 레인) 일이고 이 작업은 만들지 않는다.

## 완료 기준 (단위 테스트, 가짜 `PayPalClient`만)
- [ ] `splitRange`: 31일 이하면 조각 1개, 90일이면 조각 3개이고 겹치지 않으며 처음과 끝이 입력과 같다. 경계가 달·윤년을 지나도 맞다
- [ ] `buildTransactionsPath`: `start_date`·`end_date`가 ISO 꼴, `fields=all`, `page`·`page_size`가 들어가고 `page_size` 501은 거부. 경로에 공백·`://`가 없다
- [ ] 가짜 응답(2쪽 이상 + 기간 조각 2개)을 읽어 `sales`·`saleCount`·`byItem`·`byCountry`가 손으로 센 값과 같다. 환불(음수)은 `refundCount`에만 들어간다. 상태가 완료가 아닌 거래는 세지 않는다. 같은 `transactionId`가 두 조각에 있으면 한 번만 센다
- [ ] 금액 "48.00" → 4800, "0.05" → 5, "1,234.50"처럼 PayPal이 주지 않는 꼴은 `unexpected_response`. 부동소수점을 쓰지 않는다 (글자로 자른다)
- [ ] **개인정보**: fixture에 일부러 넣은 이름·이메일·주소·`payer_id`가 `TransactionSummary`를 `JSON.stringify`한 글자에 하나도 없다. 오류 결과·`refreshFailed`에도 없다
- [ ] 캐시: 첫 호출은 `cached: false`(호출 N회), TTL 안 두 번째 호출은 `cached: true`(호출 0회)이고 `fetchedAt`이 첫 호출 시각이다. TTL이 지나면 다시 읽는다. `forceRefresh`는 TTL 안에서도 다시 읽는다
- [ ] 새로 읽다 실패했는데 옛 캐시가 있으면 `ok: true, cached: true, refreshFailed`가 있다. 캐시도 없으면 `ok: false`. 401/403 → `not_permitted`, 429 → `rate_limited`
- [ ] `client === null`: 호출 0회, 캐시가 있으면 `cached: true`, 없으면 `paypal_unavailable`
- [ ] 가짜 클라이언트에 `call`(POST)을 달아 두고 호출 0회를 확인한다. `get`이 받은 경로가 모두 `/v1/reporting/transactions`로 시작한다
- [ ] 잘못된 기간(시작 > 끝, 94일, 날짜가 아닌 글자)은 호출 0회로 `invalid_range`
- [ ] `npm test`, `npx tsc --noEmit`, `npm run lint`, `npm run test:acceptance` (실패 0 — 단, 지금 main에서 이미 실패하는 항목이 있으면 그 목록을 보고서에 적고 이 작업과 무관함을 밝힌다)

## 하지 않을 것
- 실제 PayPal 호출, `.env` 읽기·만들기, 샌드박스가 아닌 주소
- 시뮬레이션 입력 만들기·손실 계산 (`src/engine/`), 화면 만들기·배지 문구 (`src/app/`, `config/copy.*`)
- 분쟁 연결(`GET /v1/customer/disputes`의 `disputed_transactions`와 잇기): 분쟁 읽기는 `src/paypal/disputes.ts`와 `src/app/_server/disputes.ts`가 이미 한다. 이 작업은 거래만 읽는다
- 거래 상세 보관·파일 저장·DB
- 계약(`src/types.ts`)·인수 테스트 수정 (필요하면 보고서에 요청). AC25는 컨트롤 타워가 쓴다

## 컨트롤 타워에 요청할 결정
1. **T013에 거래 수 칸을 더할지.** 지금 T013 표에는 "샌드박스 거래 n건 · cached" 칸이 없다. 더하지 않으면 이 작업의 결과는 쓰는 곳이 없다 (SPEC 2장의 "S2 실제 API = Transaction Search"가 화면에서 안 보인다). 더한다면 한 줄짜리 칸(이름이 시드 상품과 맞는 상품의 거래 수 + cached 배지)을 후속 ui 작업으로 낸다.
2. **서버가 다시 뜨면 메모리 캐시가 빈다.** 녹화 때 'cached'를 보이려면 (a) 녹화 직전에 한 번 실호출로 캐시를 데워 두거나 (b) 개인정보 없는 `TransactionSummary`를 파일(`tests/fixtures/` 같은 곳)에 스냅샷으로 두고 실패 시 읽게 하는 것 중 정해야 한다. 추천: (a). (b)는 "캐시"가 아니라 시연용 데이터라서 README 정직성 표에 적어야 한다.
