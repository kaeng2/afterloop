## 배경
지금 `PayPal-Request-Id`는 `<planId>:<엔드포인트>`이고 실제 분쟁에서는 64자가 된다 (주문 API에서 확인된 길이는 61자까지). 첫 실제 전송이 시연 녹화 순간이라 길이 문제를 미리 없앤다. 또 지금은 같은 분쟁의 두 번째 메시지가 같은 요청 번호가 되어 PayPal이 새 전송으로 처리하지 않는다.

## 수정 가능 폴더
- `src/exec/` (`request.ts` 중심)
- `tests/unit/execute.test.ts` (필요하면 `tests/unit/exec-*.test.ts` 새 파일)

이 밖은 수정하지 않는다. 특히 `src/types.ts`(계약 — `ApiRequest.requestId: string` 그대로), `src/engine/`(`planId` 만드는 방식 그대로), `tests/acceptance/`.

## 고칠 것
1. `requestIdFor`를 **hash(계획 ID + 엔드포인트 이름 + 실제로 보내는 본문)** 에서 만든 **36자 이하** 문자열로 바꾼다.
   - 본문 = PayPal로 나가는 요청 본문 그대로 (send-message는 채운 메시지, make-offer는 `note`·금액·제안 유형, accept-claim은 그 본문). 구분자가 모호하지 않게 조합한다 (예: 길이 접두 또는 JSON 직렬화 — 키 순서가 고정되게)
   - 해시는 `node:crypto`의 SHA-256. 결과는 `[A-Za-z0-9-]`만 쓰고, 사람이 로그에서 알아볼 수 있게 짧은 고정 접두(예: `al-`)를 붙여도 된다. 전체 36자 이하
   - **결정적**: 같은 계획 + 같은 본문 → 항상 같은 값 (재시도·중복 클릭이 같은 번호로 나가 PayPal이 한 번만 처리한다)
   - 메시지가 한 글자라도 다르면 다른 값 (같은 분쟁의 두 번째 메시지가 나간다). 금액이 다르면 다른 값
   - 요청 번호에 메시지 원문·금액·분쟁 ID가 그대로 드러나지 않는다 (해시만)
2. 요청 번호를 만드는 곳이 `request.ts` 한 곳인지 확인한다 (`src/exec/` 안에 `planId:`를 직접 이어 붙이는 다른 곳이 있으면 같이 고친다). `scripts/`의 주문·캡처 요청 번호(`afterloop-order-O01` 등)는 이 작업 범위가 아니다 (고치지 않는다).
3. 주석·문구에서 옛 형식(`<planId>:<엔드포인트 이름>`) 설명을 사실에 맞게 고친다.

## 완료 기준 (단위 테스트, 가짜 호출만)
- [ ] send-message·make-offer·accept-claim 모두 요청 번호 길이 ≤ 36, 문자 집합 `[A-Za-z0-9-]`
- [ ] 같은 입력으로 100번 만들어도 같은 값. 시각·난수·프로세스 정보에 기대지 않는다
- [ ] 메시지만 다른 두 실행 → 다른 값. 금액만 다른 두 제안 → 다른 값. 엔드포인트만 다르면 → 다른 값
- [ ] 아주 긴 메시지(2000자), 한국어·이모지 메시지, 실제 길이의 분쟁 ID(`PP-R-GMS-10197661`)와 계획 ID에서도 ≤ 36
- [ ] 요청 번호 문자열에 메시지 조각·분쟁 ID·금액이 들어 있지 않다
- [ ] 기존 단위 테스트 통과 (옛 형식 `…:send-message`를 기대하던 곳은 새 규칙으로 바꾸고, 바꾼 곳을 보고서에 적는다)
- [ ] `npm run test:acceptance` 실패 0 — 단, 지금 main의 AC8 "합의 단계에 증빙 링크와 메시지 링크가 함께 있으면…" 1건은 T040(엔진)이 병합되기 전이라 실패한다. 그 1건만이면 정상이고 보고서에 적는다
- [ ] `npm test`, `npx tsc --noEmit`, `npm run lint`
- [ ] 실제 PayPal 호출 0회 (`.env`를 찾지 않는다)
