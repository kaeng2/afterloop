| 항목 | 값 |

| 레인 | paypal |

**worktree 판단 근거.** 이 작업의 코드는 `src/paypal/`에 놓인다 (앱 서버가 부르는 함수이고, 앱은 `scripts/`를 import하지 않는다 — T016). `../afterloop-wt/paypal`은 `src/**`가 잠겨 있고 `scripts/`만 열려 있어 맞지 않는다. `../afterloop-wt/paypal-client`는 `src/paypal/`·`tests/`가 열려 있고 `scripts/**`·`config/**`·`package.json`이 잠겨 있다 (`settings.local.json`의 deny 확인) → 이쪽으로 정했다. 또 `paypal-client`에는 `.env`가 없어 실수로 열 일이 없다. 대가: `scripts/sandbox/setup-steps.ts`를 고칠 수 없다 → "판정 한 곳" 문제는 아래 3번에서 테스트로 묶어 풀고, 스크립트 쪽 정리 작업은 내지 않기로 했다 (결정됨).

> **가장 중요한 규칙 (맨 위)**
> 1. **실호출 시험은 O03 한 건만이다. O05·O07에는 어떤 경로로도 호출하지 않는다** (녹화용 — 추적 등록은 되돌릴 수 없다). 이 작업 중에는 실제 PayPal 호출을 **한 번도 하지 않는다.** 가짜 클라이언트(`PayPalClient`를 흉내 내는 객체)만 쓴다. 병합 뒤 컨트롤 타워가 O03 한 건으로 실제 등록을 시험한다.
> 2. **열린 분쟁이 있는 주문에는 등록하지 않는다** (SPEC 9-3). 연습용·시연 제외 분쟁이 가리키는 주문도 포함. 호출 **전에** 뺀다 (조회 GET도 하지 않는다).
> 3. 기본은 "보내지 않음"이다. 실제 전송 스위치가 꺼져 있으면 PayPal 호출이 0회다.
> 4. `/v1/shipping/trackers*`는 쓰지 않는다 (지원 중단, 이 앱에서 403). 주문별 `POST /v2/checkout/orders/{id}/track`만.
> 5. 이 worktree에 `.env`가 없다. 찾거나 만들지 않는다. Client Secret·토큰·구매자 개인정보가 결과·오류·로그에 들어가지 않는다.

## 배경
- S3 화면(T016)은 "미등록 주문 목록 → 선택 → 일괄 등록 → 건별 결과"를 보여 준다. 화면 문구 "✓ N trackers added · POST /v2/checkout/orders/{id}/track × N · 200"은 화면이 만든다. 이 함수는 그 문구를 만들 **값**만 돌려준다.
- 지금 추적 등록 코드는 `scripts/sandbox/setup-steps.ts`(`runTrack`, `planTrack`, `trackingNumberFor`, `trackRequestId`, `disputedOrderKeys`, `trackDisputedNote`)에만 있다. 앱은 이것을 import하지 않는다.
- **주의: 스크립트의 `planTrack`과 앱이 원하는 판정은 방향이 다르다.** `planTrack`은 manifest에서 `tracked: true`인 주문(= 스크립트가 등록하려는 주문)을 가려내고 그중 분쟁 걸린 것을 뺀다. 앱은 **PayPal 주문 상세에 추적이 없는 주문**(manifest의 `tracked: false`인 O02·O03·O04·O05·O07·O13이 후보)에서 분쟁 걸린 것을 뺀다. 둘이 같은 것은 "**분쟁이 걸린 주문 키 집합**"(`disputedOrderKeys`)과 제외 사유 글(`분쟁 진행 중이라 제외`)이다. 이것이 "한 곳에서 쓸 판정"이다.
- 주문 배분 (SPEC 9-3, 사람 확정): O03 = 실호출 시험용 1건. O04 = 연습용 분쟁이 걸려 있어 제외 대상. O05·O07 = 녹화용. 지금 열린 분쟁이 가리키는 주문: O01(D2-old, 시연 제외)·O02(D1)·O04(P1, 연습용·시연 제외)·O08(D3)·O13(D2) — `tests/sandbox/manifest.json`의 `disputes[].orderKey` 전부.

## 수정 가능 폴더
- `src/paypal/track.ts` (새 파일, 판정·등록 함수), `src/paypal/track-orders.ts` (새 파일, 주문 목록 읽기 — 1번 결정에 따라 얇게)
- `tests/unit/track.test.ts` (새 파일)

이 밖은 수정하지 않는다. 특히 `scripts/` (이 worktree에서 잠겨 있다), `config/`, `package.json`, `src/types.ts`, `src/exec/`, `src/app/`, `tests/sandbox/` (manifest는 읽기만, 한 글자도 바꾸지 않는다), `tests/acceptance/`, `SPEC.md`, `tasks/`. `src/paypal/client.ts`·`disputes.ts`·`mapper.ts`는 읽고 그대로 쓴다.

## 만들 것

### 1. 주문 목록과 미등록 판정
앱이 샌드박스 주문 목록(O01~O13: 키, 주문 ID, 구매자, 상품)을 어디서 읽을지 선택지:

| 선택지 | 내용 | 계약·SPEC 변경 |
|---|---|---|
| A. 앱이 `tests/sandbox/manifest.json`을 직접 읽는다 | 주문 13건과 분쟁 5건(연습용·시연 제외 포함)이 이미 여기 있다. 작은 읽기 함수가 zod로 검증한다 (모양은 `scripts/sandbox/manifest.ts`의 `ManifestSchema`와 같게 **복사**한다 — `scripts/`를 import하지 않는다) | 없음 |
| B. `config/`에 주문 표를 새로 둔다 (`config/demo-links.json`처럼 컨트롤 타워가 관리) | 배포 폴더에서 `tests/`에 기대지 않는다. 새 파일의 모양이 계약 | **필요** (SPEC 12장 설정 파일 표, `src/types.ts` 타입, 인수 테스트) |
| C. `config/demo-links.json`에 주문 칸을 더한다 | 파일 하나로 끝나 보이지만 이 파일은 "분쟁 ↔ 시드" 표다. 연습용 분쟁(O04)이 `carrierOrderId: null`이고 D2가 가리키는 주문(O01)이 실제(O13)와 달라서, **분쟁이 걸린 주문을 이 파일만으로 만들 수 없다** | **필요** (모양 변경, AC29가 모양을 지킨다) |

**결정됨 (컨트롤 타워): A.** 이유: 분쟁이 걸린 주문을 틀림없이 아는 곳이 manifest뿐이다 (연습용 O04, D2 = O13. C는 정보가 빠져 있다). 계약 변경 없음. **배포에서도 들어가도록 `fs.readFileSync`가 아니라 JSON을 정적으로 import한다** (`import manifestJson from '../../tests/sandbox/manifest.json'` 꼴. 묶음에 포함된다. `resolveJsonModule`이 켜져 있는지 `tsconfig.json`에서 확인하고, 상대 경로 import가 `@/` 규칙과 린트에 맞는지 본다. 안 되면 멈추고 보고).

구현:
- `readTrackOrders(source?)` → `{ orders: {key, orderId, buyer, sku, captureId?}[], disputes: {key, disputeId?, orderKey, demoExcluded?}[] }`. 기본 `source`는 위에서 정적으로 import한 manifest JSON이다 (테스트는 다른 값을 넘겨 쓴다). 작은 zod 스키마로 검증하고 모양이 틀리면 예외 (추측하지 않는다). 스키마: `scripts/sandbox/manifest.ts`의 `ManifestSchema`는 레인 경계(`src/`에서 `scripts/` import 금지, 그 파일은 `env.ts`도 끌고 온다) 때문에 import하지 않고 **같은 모양을 한 번 더 정의**한다. 두 스키마가 실제 `tests/sandbox/manifest.json`을 똑같이 받아들이고 같은 결과를 내는지, 틀린 모양은 둘 다 거부하는지를 테스트로 묶는다 (테스트가 `scripts/sandbox/manifest.ts`를 import하는 것은 읽기 용도로 허용). 읽은 값에 PayPal 비밀값은 없다.
- 미등록 판정 `isOrderUntracked(orderDetailBody)`: SPEC 9-3대로 주문 상세 `GET /v2/checkout/orders/{id}`의 `purchase_units[].shipping.trackers`와 캡처의 `trackers`를 본다. 취소된(`CANCELLED`) 추적은 세지 않는다 (`scripts/sandbox/paypal.ts`의 `hasTracker`와 같은 규칙이므로 **같은 동작을 테스트로 고정**한다. 이 작은 읽기 함수는 `scripts/`를 import할 수 없어 복사본이 생긴다 — 보고서에 적는다).
- `listUntracked(client, orders, disputes)` → 주문마다 `{ key, orderId, state: 'untracked' | 'tracked' | 'unknown', excluded: boolean, disputeKeys?: string[] }`. **분쟁 걸린 주문은 GET도 하지 않고** `excluded: true`로 돌려준다 (화면이 회색 + "분쟁 진행 중이라 제외"를 그린다). 조회 실패는 그 행만 `unknown` + 이유 (나머지는 계속).

### 2. 등록 함수 `registerTrackers`
```ts
registerTrackers(client, {
  orders,                  // readTrackOrders 결과
  disputes,
  selectedKeys: string[],  // 화면에서 고른 주문 키
  live: LiveGate,          // 4번의 스위치와 허용 목록
}) → Promise<TrackBatchResult>
```
- 주문 키마다 **건별 결과** 하나. 결과 상태 (이름은 제안, 구현이 정하되 보고서에 적는다):

| `result` | 뜻 | PayPal 호출 |
|---|---|---|
| `added` | `/track` 성공 | GET 1 + POST 1 |
| `failed` | 조회 또는 `/track` 실패 (상태 코드·요약 이유) | 있음 |
| `skipped_already_tracked` | 주문 상세에 이미 추적이 있다 | GET 1 |
| `excluded_dispute` | 분쟁이 걸려 호출 전에 뺐다. 사유 "분쟁 진행 중이라 제외" | **0** |
| `not_allowed` | 허용 목록에 없다 (4번) | **0** |
| `dry_run` | 스위치가 꺼져 있어 보내지 않았다 | **0** |
| `unknown_order` | `selectedKeys`에 manifest에 없는 키 | **0** |

- 건별 결과 칸: `dryRun: boolean`, `key`, `orderId`, `result`, `status`(받은 HTTP 상태 코드 또는 `null`), `trackingNumber`(등록했거나 등록하려던 값 또는 `null`), `note`(짧은 이유. 서버 오류 요약은 `name`·`details[].issue`·`debug_id`만. 사람이 쓴 설명·요청 본문·비밀값은 넣지 않는다), `virtualTracking: true`(5번).
- 묶음 결과: `{ results: [...], mode: 'live' | 'dry_run', dryRun: boolean, counts: { added, failed, skipped, excluded, notAllowed, dryRun } , statusCodes: number[] /* 성공한 건의 실제 상태 코드, 중복 없이 */ }`. 화면은 이 값으로 "N trackers added · … × N · <상태 코드>"를 만든다. 문구 자체는 화면이다.
- 호출 규칙: 주문별로 GET `/v2/checkout/orders/{id}` → 추적 없음이면 POST `/v2/checkout/orders/{id}/track` (`capture_id`는 manifest 값, 없으면 주문 상세의 첫 캡처). 본문과 `trackRequestId`(`afterloop-track-<키>`: 같은 주문을 다시 보내도 같은 요청 번호 → 중복 등록 방지)는 스크립트와 **같은 값**을 쓴다. 한 건이 실패해도 **나머지는 계속**한다 (던지지 않는다. 클라이언트가 던지는 예외는 그 건의 `failed`로 바꾼다).
- 순서: `selectedKeys`가 아니라 manifest 순서로 돌려준다 (화면 표와 같은 순서).

### 3. 안전 규칙 판정 — 한 곳 (SPEC 9-3)
- `src/paypal/track.ts`에 **순수 함수** 두 개를 둔다:
  - `disputedOrderKeys(disputes)` → `Map<주문 키, 분쟁[]>` (연습용·시연 제외 포함 — 시연에서 뺐을 뿐 PayPal에서는 살아 있다)
  - `trackDisputedNote(disputes)` → `분쟁 진행 중이라 제외 (D2-old · 시연 제외)` 꼴의 사유 글 (스크립트의 `trackDisputedNote`와 같은 글자). 화면에는 분쟁 번호·내용을 내지 않는다 (T016) — 화면용으로는 `excluded: true`와 고정 사유 `TRACK_DISPUTED_NOTE`만 쓰게 하고, 분쟁 키가 든 긴 글은 보고서·로그용으로 둔다.
- **"판정을 두 벌 두지 않는다"를 이렇게 지킨다.** 이 worktree에서는 `scripts/`를 고칠 수 없으므로 이번 작업에서는 위 두 함수를 `src/paypal/track.ts`가 **정본**으로 가지고, 스크립트의 같은 이름 함수(`scripts/sandbox/setup-steps.ts`)는 그대로 둔다. 대신 **같은 결과가 나온다는 것을 테스트로 고정**한다: 실제 `tests/sandbox/manifest.json`을 읽어 두 구현의 `disputedOrderKeys` 결과가 같고(키 집합과 분쟁 목록), `trackDisputedNote` 글이 같다. 테스트가 `scripts/sandbox/setup-steps.ts`를 import하는 것은 읽기 용도로 허용한다. 둘이 어긋나면 이 테스트가 실패한다.
- 결정됨 (컨트롤 타워): 스크립트를 `src/paypal/track`으로 옮기는 후속 작업은 **내지 않는다.** 두 구현이 같은 결과를 낸다는 위 테스트가 유일한 묶음이다. 이 작업에서 스크립트는 건드리지 않는다.
- 분쟁 판정은 `selectedKeys`가 무엇이든 `registerTrackers` 안에서 **다시** 한다 (화면이 이미 뺐다고 믿지 않는다. T016: 서버 액션에 직접 넣어도 그 주문의 `/track` 호출은 0회).
- 목록에 없는 주문 키·분쟁 정보가 비어 있는 상태(`disputes`가 빈 배열인데 manifest에는 있는 경우)는 `readTrackOrders`가 항상 manifest 전체를 읽어 넘기도록 해서, 호출하는 쪽이 `disputes`를 빼먹고 넘길 수 없게 한다 (`registerTrackers`는 `disputes`를 받지 않고 `readTrackOrders` 결과 한 덩어리를 받는 모양을 권장).

### 4. 실수로 O05·O07을 등록하지 않게 하는 장치 (확정)
**기본은 꺼짐 = `dry_run`.** 아래 세 이름은 확정이다. 환경 변수는 **서버에서만** 읽는다 (화면 서버 액션 한 곳에서 `liveGateFromEnv(process.env)`로 `LiveGate`를 만들어 이 함수에 넘긴다. 이 함수들은 환경 변수를 직접 읽지 않는다. `NEXT_PUBLIC_` 이름을 쓰지 않는다).
1. **`AFTERLOOP_TRACK_LIVE`**: 값이 `1`일 때만 `enabled: true`. 그 밖(없음·`0`·다른 값)은 꺼짐. T009의 메시지 전송 스위치와 **별개**다 (하나를 켠다고 다른 것이 켜지면 안 된다).
2. **`AFTERLOOP_TRACK_LIVE_ORDERS`**: 쉼표로 구분한 주문 키. **없으면 기본 허용은 `O03` 하나.** 스위치가 켜져 있어도 이 목록에 없는 주문에는 호출하지 않는다 (`not_allowed`, 호출 0회). 키 앞뒤 공백·소문자는 정리하고, manifest에 없는 키는 무시한다.
3. **`AFTERLOOP_TRACK_RECORDING`**: 값이 `1`일 때만 `recordingConfirmed: true`. **O05·O07(`RECORDING_ORDER_KEYS`, 이름 붙인 상수)은 이 값이 켜져 있을 때만 허용 목록에 넣을 수 있다.** 꺼져 있는데 `AFTERLOOP_TRACK_LIVE_ORDERS`에 O05나 O07이 있으면 `liveGateFromEnv`가 그 키를 허용 목록에서 **빼고** (그리고 `registerTrackers`도 한 번 더 확인해 `not_allowed`로 돌려준다), 호출 0회. 즉 녹화 당일에 사람이 세 변수를 모두 설정해야만 O05·O07이 나간다. 컨트롤 타워의 O03 시험 때는 `AFTERLOOP_TRACK_LIVE=1`만 켜면 O03 한 건만 나간다.
- **스위치가 꺼져 있을 때(`dry_run`)**: PayPal 호출 **0회** (GET도 없음). 건별 결과 `result: 'dry_run'`, `status: null`, `trackingNumber`는 등록하려던 가상 값, 그리고 **결과에 `dryRun: true`** (건별과 묶음 모두). 화면(T016)이 이 값을 보고 "Dry run — no call was made"로 보인다. `added`나 상태 코드 200을 **만들어 내지 않는다.** 묶음 `mode`는 `'dry_run'`.
- `.env.example`에 이 세 이름이 있어야 하면 **컨트롤 타워가 넣는다** (작업 세션은 `.env.example`을 고치지 않는다). 보고서에 이름과 기본값만 적는다.

### 5. 등록할 추적번호의 출처
- 스크립트와 같은 규칙: `trackingNumberFor(키)` = `FKAL` + 키의 숫자 두 자리 + `2026` (예: O03 → `FKAL032026`), 운송사 `OTHER`, `carrier_name_other` = `Fernwood Knits demo carrier`, `notify_payer: false`. 같은 키는 항상 같은 번호. 본문에 개인정보를 넣지 않는다.
- 결과 칸 `virtualTracking: true`를 모든 건에 싣는다. 화면이 'Demo data' 배지를 붙일 때 쓴다 (배지를 붙일지는 T016의 사람 확인 2번).
- `trackingNumberFor`·`trackRequestId`·`CARRIER_NAME_OTHER`도 스크립트와 같은 값이 나오는지 3번처럼 테스트로 고정한다.
