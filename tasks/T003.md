## 목표
PayPal 분쟁 목록·상세 응답을 읽어 엔진이 쓰는 `BoardState`(`@/types` 1부)로 바꾼다 (SPEC v2.2 9-4장). 화면(S4 Inbox, S5 Case)과 오토파일럿의 입력이다. 이 작업은 **조회만** 한다.

## 입력 / 출력 타입
- `PayPalClient` (`@/types` 4부. `get(path)`만 쓴다), `BoardState`, `MoveType`
- 공개 함수
  - `src/paypal/disputes.ts`
    - `listDisputes(client, opts?)` → 분쟁 요약 배열. `GET /v1/customer/disputes?page_size=…` (쿼리 값은 퍼센트 인코딩). `links[rel=next]`가 있으면 다음 쪽까지 (최대 쪽 수를 상수로 제한)
    - `getDispute(client, disputeId)` → 상세 원본(`unknown`을 zod로 검증한 값). `GET /v1/customer/disputes/{id}`. `disputeId`는 PayPal 형식(`PP-`로 시작하는 영문·숫자·하이픈)만 받고 그 밖은 호출 전에 예외
  - `src/paypal/mapper.ts`
    - `toBoardState(detail, extra)` → `BoardState`. `extra`는 PayPal 응답에 없는 값: `{ hasTracking, hasDeliveredTracking, buyerPriorInrDisputes, isDemo, cause? }` (추적은 주문 상세에서, 이전 분쟁 수는 목록에서, 원인은 분류기에서 온다. 이 함수는 받기만 한다)
    - `countPriorInrDisputes(disputes, buyerKey, currentDisputeId)` → 같은 구매자의 이전 미수령(INR) 분쟁 수 (이번 건 제외)

## 변환 규칙
| `BoardState` | PayPal 상세 응답 | 비고 |
|---|---|---|
| `disputeId` | `dispute_id` | |
| `reason` | `reason` | 그대로 (`MERCHANDISE_OR_SERVICE_NOT_RECEIVED` 등) |
| `stage` | `dispute_life_cycle_stage` | `INQUIRY` / `CHARGEBACK` / `PRE_ARBITRATION` / `ARBITRATION`. `types.ts`의 `BoardState['stage']`가 받는 값만. 모르는 값이면 예외 (조용히 기본값으로 바꾸지 않는다) |
| `channel` | `dispute_channel` | `INTERNAL` / `EXTERNAL` (카드사 분쟁은 오토파일럿이 건너뛴다) |
| `dueDate` | `seller_response_due_date` (없으면 `buyer_response_due_date`) | ISO 8601 그대로. 둘 다 없으면 타입이 허용하는 방식으로 (타입을 먼저 읽는다) |
| `amountCents` | `dispute_amount.value` | **문자열을 부동소수로 곱하지 않는다.** `"48.00"` → 4800을 문자열 자리 연산으로. `currency_code`가 `USD`가 아니면 예외 |
| `currency` | `dispute_amount.currency_code` | `'USD'` |
| `allowedMoves` | `links[].rel` | `make_offer` → `make_offer`, `send_message` → `send_message`, `accept_claim` → `accept_claim`, `provide_evidence` → `provide_evidence`. 그 밖의 rel(`self`, `escalate`, `acknowledge_return_item` 등)은 버린다. 순서는 고정 (타입 선언 순서) |

- 응답은 신뢰하지 않는 입력이다: zod로 필요한 필드만 검증하고, 모르는 필드는 무시한다. 필수 필드가 없으면 어떤 필드인지 알 수 있는 예외 (값은 싣지 않는다)
- **개인정보**: 구매자 이름·이메일·주소·메시지 원문을 `BoardState`·로그·예외 문구에 넣지 않는다. `buyerKey`는 `disputed_transactions[].buyer.payer_id`(없으면 그 필드가 없다는 예외)처럼 식별자만 쓴다
- 구매자 메시지 원문과 추적 이벤트 텍스트가 필요한 분류 입력(`ClassifyInput`)은 별도 함수 `toClassifyInput(detail, extra)`로 만든다: `buyerMessages`는 `messages[]` 중 `posted_by: 'BUYER'`의 `content`만, 개인통관고유부호 모양(`P` + 숫자 12자리)은 가리지 않고 그대로 넘긴다 (가리는 것은 분류기 T006의 일). 로그에는 남기지 않는다

## 같이 고칠 것 (T002 재검증 보고 `reports/T002-verify.md`)
`src/paypal/client.ts`의 path 표기(`labelPath` 주변): 비밀값을 가리기 **전에** 제어문자(`\n`, `\r`, `\t`, NUL, DEL 등)를 지운다. 지금은 가린 뒤에 지워서, 제어문자로 쪼개 넣은 비밀값이 거부 에러의 `message`·`path`에 다시 이어 붙어 나온다. 단위 테스트 추가 (가짜 Secret을 `\n`으로 쪼갠 path → 에러·로그 어디에도 이어 붙은 값이 없음). AC14(14개)와 기존 단위 테스트는 그대로 통과해야 한다
