> **가장 중요한 규칙**
> 1. `.env`를 찾거나 만들지 않는다.
> 2. **이 작업은 실제 PayPal 호출을 한 번도 하지 않는다.** `npm run sandbox:*`를 실행하지 않는다 (병합 뒤 컨트롤 타워가 `npm run sandbox:disputes`를 한 번 돌려 확인한다). 가짜 클라이언트·예시 자료 단위 테스트만 한다.
> 3. `tests/sandbox/manifest.json`, `tests/sandbox/last-run.md`는 바꾸지 않는다.
> 4. 구매자 글 원문은 로그·출력·예외 문구·보고서에 싣지 않는다 (지금 규칙 그대로. 개수만 싣는다).

## 실제로 본 것 (2026-11-10, 값은 개인정보·비밀값을 뺀 꼴만)
분쟁 3건의 `GET /v1/customer/disputes/{id}` 응답:

| | D1 (SNAD) | D2·D3 (INR) |
|---|---|---|
| `dispute_life_cycle_stage` | `INQUIRY` | `CHARGEBACK` (채널은 `INTERNAL`) |
| `status` / `dispute_state` | `WAITING_FOR_SELLER_RESPONSE` / `REQUIRED_ACTION` | `UNDER_REVIEW` / `UNDER_PAYPAL_REVIEW` |
| `seller_response_due_date` | 있음 | **없음** (`buyer_response_due_date`도 없음) |
| `messages` | 1건 (`posted_by: "BUYER"`) | **키 자체가 없음** |
| `evidences` | 1건 | 1건 |
| `links[].rel` | `self`, `accept_claim`, `send_message`, `escalate`, `make_offer` | `self`, `provide_supporting_info` |

세 건 모두 `evidences`는 이런 꼴이고, 구매자가 접수할 때 쓴 글이 `notes`에 들어 있다 (D1은 `messages[0].content`와 **같은 글**이다):

```json
"evidences": [
  { "evidence_type": "CREATE", "notes": "<구매자가 쓴 글>", "source": "SUBMITTED_BY_BUYER", "date": "2026-11-09T23:40:09.334Z", "dispute_life_cycle_stage": "INQUIRY" }
]
```

지금 `toClassifyInput`은 `messages`만 읽어서 D2·D3의 `buyerMessages`가 빈 배열이 된다. 분류기와 확대 위험 신호가 구매자 글을 못 본다.

## 수정 가능 폴더
- `src/paypal/disputes.ts`, `src/paypal/mapper.ts`
- `tests/unit/disputes.test.ts`, `tests/unit/mapper.test.ts`
- `tests/fixtures/` (새 예시 자료 추가만. 있는 파일은 바꾸지 않는다)

이 밖은 수정하지 않는다. 특히 `src/types.ts`(계약), `tests/acceptance/`, `src/engine/`, `src/exec/`, `src/ai/`, `scripts/` (이 worktree에서는 잠겨 있다. 출력 칸 추가는 T038로 뺐다).

## 고칠 것
1. **스키마** (`disputeDetailSchema`): `evidences`를 선택 필드로 받는다 — 항목마다 `evidence_type`·`notes`·`source`·`date` 모두 선택 문자열. 모르는 키는 지금처럼 통과시킨다. `evidences`가 없거나 빈 배열이어도 된다.
2. **`toClassifyInput`의 `buyerMessages`** (계약 `ClassifyInput`은 그대로):
   - 지금처럼 `messages` 중 `posted_by`가 `BUYER`인 글
   - **더하기** `evidences` 중 `source`가 `SUBMITTED_BY_BUYER`이고 `notes`가 비어 있지 않은 글
   - 같은 글(앞뒤 공백을 뺀 뒤 완전히 같은 문자열)은 한 번만 넣는다 (D1처럼 `messages`와 `evidences`에 같은 글이 있으면 1건)
   - 순서: 시각(`time_posted` / `date`)이 있는 글을 시각순(이른 것부터, `Date.parse`로 비교 — 문자열 비교 금지)으로 먼저, 시각이 없거나 읽을 수 없는 글은 그 뒤에 원래 순서(`messages` 먼저, 그다음 `evidences`)로. 시각이 같으면 원래 순서. 같은 입력이면 항상 같은 순서
   - 같은 글이 둘이면 먼저 오는 것을 남긴다
   - 판매자·PayPal이 낸 증빙(`source`가 `SUBMITTED_BY_SELLER` 등)의 `notes`는 넣지 않는다
3. (T038로 옮김 — `npm run sandbox:disputes` 출력 칸 추가는 이 작업에서 하지 않는다)
4. **예시 자료**: `tests/fixtures/dispute-detail.claim-under-review.json`은 1차 시도가 이미 만들었다 (확인만 하고, 모자라면 고친다) — 위 표의 D2 꼴 (`messages` 키 없음, `evidences` 1건, `links`는 `self`·`provide_supporting_info`, 기한 없음). 금액 72.00 USD, reason `MERCHANDISE_OR_SERVICE_NOT_RECEIVED`. 구매자 글은 아래 문장을 쓴다. 이름·이메일·주소·`payer_id`는 지어낸 값(`TESTBUYER00001` 같은 꼴)으로 넣고 실제 값을 쓰지 않는다:

   ```
   벌써 3주째인데 아직도 안 왔어요. 배송 조회를 해 봐도 며칠째 같은 단계에서 멈춰 있고, 판매자에게 메시지를 보냈는데 답도 없어요. 선물하려고 산 스웨터라 더 기다리기 어렵습니다. 이번 주 안에 연락 없으면 카드사에 이의제기할게요.
   ```

## 바꾸지 않는 것 (보고서에 사실만 적는다)
- `toBoardState`: `CHARGEBACK` 단계, 빈 `dueDate`, 빈 `allowedMoves`는 지금 그대로 둔다 (`provide_supporting_info`는 계약의 `MoveType`에 없다. 계약을 바꿀지는 사람이 정한다)
