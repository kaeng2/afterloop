## 수정 가능 폴더
- `src/engine/escalation.ts` (새 파일)
- `src/engine/params.ts`: 확대 위험 가중치 검증에 필요한 export 추가만 (기존 동작을 바꾸지 않는다)
- `tests/unit/escalation.test.ts` (새 파일)

이 밖은 수정하지 않는다. 특히 `src/types.ts`, `tests/acceptance/`, `config/`, `src/ai/`.

## 목표
`escalationRisk(signals, rules?)` → `EscalationRisk` (SPEC v2.1 7장). 분쟁이 카드사 분쟁으로 커질 위험을 점수로 낸다. 신호를 만드는 일(메시지에서 카드사 언급 찾기, 어조 판별)은 다른 작업이고, 여기서는 **신호 → 점수**만 한다.

## 입력 / 출력 타입
- 입력: `EscalationSignals`, `PolicyConfig` (`@/types` 5부). 가중치는 `rules.escalation`
- 출력: `EscalationRisk` (`score`, `band`, `parts`)
- 공개 함수: `src/engine/escalation.ts`의 `export const escalationRisk: EscalationRiskFn`
- `rules`를 안 넘기면 `config/rules.json`을 읽는다

## 동작
| 신호 (`parts[].signal`) | 조건 | 점수 |
|---|---|---|
| `cardCompanyMention` | `mentionsCardCompany` | `rules.escalation.cardCompanyMention` (3) |
| `unanswered` | `secondMessageUnanswered` **또는** `unansweredOver24h` (둘 다여도 한 번만) | `unanswered` (2) |
| `angryTone` | `angryTone === true` (`null` = 판정 보류는 0, `false`는 0) | `angryTone` (1) |
| `dueWithin72h` | `hoursToDue <= 72` (기한이 지난 음수도 포함) | `dueWithin72h` (1) |

- `score` = 점수 합. `band`: `score >= highFrom`(5) → `'High'`, `score >= watchFrom`(3) → `'Watch'`, 그 외 `'Low'`
- `parts`: 위 네 신호를 **이 순서로 항상 4개** 넣는다 (해당 없으면 `points: 0`). 점수 합 = `score`
- 검증 (zod): 가중치는 0 이상 정수, `watchFrom <= highFrom`, `hoursToDue`는 유한한 수. 어기면 예외
- 숫자(3, 2, 1, 72 중 가중치와 구간 기준)는 코드에 쓰지 않고 `rules.escalation`에서 읽는다. 72시간 기준은 `PolicyConfig`에 필드가 없으므로 이 파일 안의 이름 붙인 상수 하나로 둔다 (계약 변경이 필요하다고 보면 보고서에 적는다)
- `Math.random`, `Date`, `performance.now` 금지. 입력 객체를 바꾸지 않는다
