### 사실값 토큰 쓰는 법 (지금 코드 기준)
- `checkTokens`에는 **원래 값** facts를 넘긴다 (날짜는 ISO `2026-11-17`). 그래야 전송본에 "11월 17일"을 직접 쓴 것을 잡는다.
- 채울 때는 값을 현지 표기로 바꾼 facts 사본을 `fillTokens`에 넘긴다: `{ ...fact, value: formatFact(fact.kind, fact.value, 'ko') }`. `fillTokens`는 `value`를 그대로 넣는다.
- 채운 한국어 글이 `executeMove`의 `messageTemplate`이다. `executeMove`는 `⟦…⟧`가 남았거나 금액을 직접 쓴 글(`$72`)을 거부한다. 답장에 금액을 쓰지 않는다 (금액 토큰 `⟦AMOUNT_n⟧`도 이 경로에서는 쓰지 않는다 — `src/ai/tokens.ts` 머리말).

### 전송 버튼이 켜지는 조건 (전부 참일 때만)
1. 영어 초안과 한국어 전송본이 있다.
2. `checkTokens(...).ok === true`.
3. "후" 보드의 답장 계획이 있고 그 실행 API가 `send_message`다 (선행 A).
4. 이 화면에서 아직 보내지 않았다.

### 전송 (서버 액션, `src/app/cases/actions.ts` + `src/app/_server/send.ts`)
브라우저가 보낸 값은 믿지 않는다. 서버가 다시 한다: 보드 만들기 → `recommend` → `planMove` → `checkTokens` → `fillTokens` → `executeMove`. 승인(`Approval`)은 누른 시각과 계획 ID로 서버가 만든다.

**기본은 가짜 전송.**
- `resolveSendMode(env)` (순수 함수): 환경 변수 `AFTERLOOP_REAL_SEND`가 정확히 `"1"`일 때만 `'live'`, 그 밖(없음, `"true"`, `"0"`, 빈 값, 공백)은 `'simulated'`. 변수 이름은 제안이다 (사람이 정하고 `.env`에 직접 넣는다. ui 레인은 `.env`·`.env.example`을 고치지 않는다).
- 가짜 전송: 네트워크를 타지 않는 `PayPalCaller`를 `executeMove`에 넘긴다. 승인·토큰·계획 검사는 진짜와 똑같이 돈다. 결과 표시는 **"Simulated — nothing was sent to PayPal"**. 진짜 응답처럼 보이는 "send-message 200"을 쓰지 않는다.

**두 번 보내지 않게 하는 장치 (실제 전송일 때 모두 적용).**
1. 허용 목록: 시연 분쟁(연결 표의 D1·D2)만. `demoExcluded` 분쟁과 목록 밖 ID는 호출 전에 거부한다.
2. 전송 직전에 `getDispute`로 다시 읽어, 판매자가 쓴 글(`messages[].posted_by`가 `SELLER`)이 이미 있으면 거부한다 ("already replied"). 서버를 껐다 켜도 막힌다.
3. `executeMove`가 같은 계획의 두 번째 실행을 호출 없이 이전 결과로 돌려준다 (이미 있는 동작). 같은 계획은 같은 `PayPal-Request-Id`를 쓴다.
4. 화면: 누르면 바로 버튼이 꺼지고, 실제 전송일 때는 확인 창("This sends a real message to PayPal sandbox dispute <번호>")을 한 번 거친다.

## 보기용 데이터를 만드는 순수 함수 (`src/app/cases/model.ts`)
DOM·네트워크·시계·난수를 쓰지 않는다. 인수 테스트(AC18)가 직접 부른다. 저장소에 DOM·브라우저 시험 도구는 없다 (새로 들이지 않는다).

- `buildCaseView(input, params?, rules?)` → 화면에 뿌릴 값 묶음. `input`: 구매자·상품, 대화 글 배열(출처 표시 포함), 전 보드, 후 보드, 배송사 이벤트, 지금 신호·답장 후 신호(없으면 `null`), 코칭·영어 초안·한국어 전송본(없으면 `null`), `facts`, 전송 방식, 전송 상태. 안에서 `recommend`·`escalationRisk`·`checkTokens`·`fillTokens`를 **그대로 불러** 결과를 옮긴다.
- `canSend(view)` → `{ ok, reason }` (위 네 조건).
- `src/app/_server/send.ts`: `resolveSendMode(env)`, `createSimulatedCaller()`, `guardLiveSend({ disputeId, allowList, detail })` (모두 네트워크 없이 시험할 수 있게).

## 심사위원 리뷰 반영 (사람 승인 전)
출처: `reports/review-20261110-1.md` 고칠 것 ①·②, 6장. 리뷰 제안은 아직 사람이 승인하지 않았다. 승인되면 위 본문에 합친다.

1. **가운데의 주인공은 "배송사 정보 반영 전 → 후" 한 줄 비교다.** 화면에서 가장 크게 보인다 (위 표 4번). 원인·근거·코칭·검사 줄은 그보다 작게 둔다.
2. 두 금액에는 **"Expected loss"(예상 손실) 이름표와 'Assumption' 배지**를 붙인다. 이름표가 없으면 "답장하는 데 왜 돈이 드나"로 읽힌다.
3. **금액 표기 — 사람 확인 필요.** 기본은 사람이 지시한 **$74.00 → $36.80** (센트까지, `centsToDisplay`). 리뷰는 **$74 → $37** (달러로 반올림. 다른 화면이 $216처럼 달러 단위라서)을 권한다. 어느 쪽이든 표기만 다르고 값은 엔진 결과 그대로다. 달러로 반올림하기로 하면 반올림 함수는 화면 공용(`src/app/_shared/money.ts`)에 하나만 두고 S2·S1과 같이 쓴다.
4. **위험 점수 6 → 3은 작은 배지로만.** 신호별 점수는 펼쳐야 보이게 해도 된다.
5. **실제와 시연용이 한눈에 갈리게.** 실제인 것: 분쟁(번호·상태·금액), 한국어 접수 글, 전송. 시연용인 것: 배송사 이벤트, 11/02 문의. 배송사 줄에 'Demo data' 배지, 전송 결과에 **"PayPal sandbox · <실제 분쟁 번호>"**. 실제 글에는 "From PayPal" 같은 출처 표시를 붙인다 (문구는 `case.*`).
6. **누르는 순간부터 응답 표시까지 화면 전환 없이 한 화면에서.** 전송 결과는 버튼 자리 바로 옆·아래에 뜬다. 다른 주소로 넘어가거나 화면을 새로 그리지 않는다. 전송 직전·직후에 전 → 후 비교가 같은 화면에 계속 보인다.
7. **실패했을 때 화면 (완료 기준에 넣는다).** 가짜 호출기로 아래를 각각 만들어, 무엇이 뜨는지 단위 테스트와 보고서에 적는다. 모두 같은 자리에 뜨고, 다음에 할 일이 한 줄 보인다.
   - 승인·토큰 검사 실패 (호출 전 거부): `executeMove`의 `error`·`nextAction` 그대로
   - PayPal이 4xx·5xx로 답함: 상태 코드와 "nothing was sent" + `nextAction` ("같은 계획을 다시 실행해도 두 번 보내지 않는다")
   - 호출이 예외로 끝남 (네트워크): 같은 자리에 다시 시도 안내
   - 이미 답장한 분쟁: "already replied" + PayPal에서 확인하라는 안내
   - 실패 뒤에도 버튼이 멋대로 다시 켜져 연타로 두 번 나가지 않는다 (다시 시도는 사람이 한 번 더 확인한 뒤)
8. 가짜 전송으로 같은 동선을 여러 번 연습할 수 있어야 한다 (가짜 전송은 "보냄" 상태를 되돌리는 [Reset]이 있어도 된다. 실제 전송에는 없다).
9. 리뷰가 짚은 위험 (결정된 것이라 논쟁하지 않는다. 화면 쪽에서 알고 있을 것): 첫 실제 `send-message`가 녹화 순간이다. 이 분쟁의 요청 번호는 64자다 (`plan-<분쟁 번호>-fight-send_message-none-none:send-message`). 61자는 주문 API에서만 확인됐다 (`reports/T001-impl.md`). 분쟁 API에서 되는지는 확인되지 않았다 (SPEC 13장 Q11).
