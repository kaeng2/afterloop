> 1. **화면은 계산하지 않는다.** 두 금액(전 7400¢, 후 3680¢)과 점수(6 → 3)는 엔진 함수의 결과를 옮긴 것이다. 화면 코드·문구 파일에 이 숫자를 적지 않는다. 표시는 달러로 반올림한다 (`$74` → `$37`). 반올림은 T047의 `toDollarsRounded` 한 곳에서만 한다.

## 장면의 사실 (SPEC 2장, 바꾸지 않는다)
- 실제 분쟁 D2는 추적번호가 **없는** 주문 O13에 걸려 있다 (합의 단계 `INQUIRY`, 미수령, 7200¢, 응답 기한 2026-11-30T00:37Z).
- 화면 설명: "판매자가 PayPal에 추적번호 등록을 빠뜨렸고, 배송사 정보에서 통관 보류를 찾아냈다."
- **실제인 것**: 분쟁(번호·상태·금액), 한국어 접수 글, 전송. **시연용인 것**: 배송사 추적·통관 이벤트, 11/02 문의 (무응답 신호가 여기에 기댄다).
- 원인은 두 경우 모두 **규칙(코드)** 이 정한다. 전: 추적 없음 + 미수령 → A1. 후: 추적 이벤트에 `Customs hold` → A2. `cause.source === 'rule'` → 'Code decides' 배지. AI가 정한 것처럼 보이게 하지 않는다. AI가 하는 일은 번역·코칭·답장 문장·어조 판정이다.

### 사실값 토큰 쓰는 법
- `facts`는 서버가 만든다 (날짜는 ISO `2026-11-17` 꼴의 원래 값). `draftReply`·`translateReply`·`checkTokens`에는 **원래 값** facts를 넘긴다.
- 채울 때는 값을 현지 표기로 바꾼 facts 사본을 `fillTokens`에 넘긴다: `{ ...fact, value: formatFact(fact.kind, fact.value, 'ko') }`.
- 채운 한국어 글이 `executeMove`의 `messageTemplate`이다. `executeMove`는 `⟦…⟧`가 남았거나 금액을 직접 쓴 글을 거부한다. 서연 답장에는 금액을 쓰지 않는다.
- 답장에 넣을 날짜(원문 예시 "by Nov 17")의 값과 출처는 **사람 확인 필요**다. 정해지기 전에는 `facts`가 빈 배열이고 초안에 날짜가 없다.

### 전송 버튼이 켜지는 조건 (전부 참일 때만)
1. 영어 초안과 한국어 전송본이 있다 (`draftReply`·`translateReply`가 `ok: true`).
2. `translateReply(...).sendable === true`.
3. "후" 보드의 답장 계획이 있고 그 실행 API가 `send_message`다 (T040).
4. 이 화면에서 아직 보내지 않았다.

### 전송 (서버 액션 `src/app/cases/actions.ts` + `src/app/_server/send.ts`)
브라우저가 보낸 값은 믿지 않는다. 서버가 다시 한다: `loadDemoDisputes` → `recommend` → `planMove` → `checkTokens` → `fillTokens` → `executeMove`. 승인(`Approval`)은 누른 시각과 계획 ID로 서버가 만든다.

**기본은 가짜 전송.**
- `resolveSendMode(env)` (순수 함수): 환경 변수 `AFTERLOOP_REAL_SEND`가 정확히 `"1"`일 때만 `'live'`, 그 밖(없음, `"true"`, `"0"`, 빈 값, 공백)은 `'simulated'`. 변수 이름은 **사람 확인 필요** (사람이 `.env`에 직접 넣는다. ui 레인은 `.env`·`.env.example`을 고치지 않는다).
- 가짜 전송: 네트워크를 타지 않는 `PayPalCaller`를 `executeMove`에 넘긴다. 승인·토큰·계획 검사는 진짜와 똑같이 돈다. 결과 표시는 **"Simulated — nothing was sent to PayPal"**. 진짜 응답처럼 읽히는 "Sent · send-message 200"을 쓰지 않는다.
- 가짜 전송은 같은 동선을 여러 번 연습할 수 있게 [Reset]으로 "보냄" 상태를 되돌릴 수 있다. 실제 전송에는 [Reset]이 없다.

**두 번 보내지 않게 하는 장치 (실제 전송일 때 모두 적용).**
1. 허용 목록 (T046): 목록에 있는 분쟁만. 연습용·시연 제외 분쟁과 목록 밖 번호는 호출 전에 거부한다.
2. 전송 직전에 `getDispute`로 다시 읽어, 판매자가 쓴 글(`messages[].posted_by`가 `SELLER`)이 이미 있으면 거부한다 ("already replied"). 서버를 껐다 켜도 막힌다.
3. `executeMove`가 같은 계획의 두 번째 실행을 호출 없이 이전 결과로 돌려준다. 같은 계획·같은 메시지는 같은 요청 번호로 나간다 (T041).
4. 화면: 누르면 바로 버튼이 꺼지고, 실제 전송일 때는 확인 창("This sends a real message to PayPal sandbox dispute <번호>")을 한 번 거친다.

**실패했을 때 화면 (모두 결과 자리에 뜨고, 다음에 할 일이 한 줄 보인다).**
| 경우 | 화면에 뜨는 것 |
|---|---|
| 승인·토큰 검사 실패 (호출 전 거부) | `executeMove`의 `error`·`nextAction` 그대로 |
| PayPal이 4xx·5xx로 답함 | 상태 코드 + "nothing was sent" + `nextAction` (같은 계획을 다시 실행해도 두 번 보내지 않는다는 안내) |
| 호출이 예외로 끝남 (네트워크) | 다시 시도 안내 |
| 이미 답장한 분쟁 | "already replied" + PayPal에서 확인하라는 안내 |

실패 뒤에 버튼이 저절로 다시 켜지지 않는다. 다시 시도는 사람이 [Try again]을 누른 뒤에만 된다. 실패하면 "답장 후 위험" 배지를 보이지 않는다.

1. **이름표에 행동을 넣는다**: 왼쪽 칸 이름 **"PayPal data only · Full refund"**, 오른쪽 **"With carrier data · Reply"**. 행동 글자("Full refund", "Reply")는 문구 파일 키에서 읽고, **어느 행동인지는 엔진 결과(`recommend(...).best.move`)에서 고른다** (refund → "Full refund", fight → "Reply", offer → "Offer"). 화면이 "환불"·"답장"을 직접 정하지 않는다.
2. **두 숫자를 같은 줄에 나란히**: `$74`는 흐린 색(보조 글자색 변수) + **취소선**, `$37`은 크게(`.hero-number`). **화살표는 두 숫자 사이 가운데** (세로로도 두 숫자의 가운데 줄에 맞춘다). 좁은 폭(30rem 아래)에서 세로로 쌓이는 것은 지금처럼 두되, 쌓일 때도 순서는 왼쪽 → 화살표 → 오른쪽.
3. **카드 안 오른쪽 빈 공간이 크지 않게 폭을 맞춘다**: 카드가 화면 폭 전체로 늘어나 숫자 오른쪽에 큰 빈칸이 생기지 않게 한다 (예: 카드 폭을 내용에 맞추거나 `max-width`를 두고, 두 칸이 카드 폭을 고르게 나눠 갖게). 1440 폭에서 두 숫자와 화살표가 카드 가운데 쪽에 모여 보여야 한다.
4. **"Expected loss" 이름표와 `Assumption` 배지는 유지.** 이 카드에서 **`Demo data` 배지는 "With carrier data" 쪽에만** 붙인다 (배송사 정보가 시연용이기 때문. 왼쪽 "PayPal data only"는 실제 데이터라 배지가 없다). 지금 카드 머리에 붙어 있는 `Demo data`는 오른쪽 칸 이름 옆으로 옮긴다. 부품에 칸별 배지 자리(예: `CompareSide.badge`)를 둔다.
5. 접근성: 취소선 숫자는 화면 읽기에서도 "이전 값"으로 읽히게 한다 (예: `<s>` 또는 `<del>` + 읽기용 글자). 화살표의 `aria-label`은 지금처럼 문구 키에서.

### 1. 배치
대화 카드와 배송사 카드를 **나란히 두지 말고 왼쪽 열에 위아래로 넓게** 쌓는다 (왼쪽 열 폭 전체를 쓴다). 순서: 머리글 → 비교 카드 → 원인 카드 → 대화 → 배송사. 오른쪽 답장 칸은 그대로. 1440에서 배송사 이벤트 글이 한 줄에 들어가야 한다. 390에서는 지금처럼 한 열.

### 2. 이름 (인사말·서명) — AI에 값을 보내지 않는다
- (T056이 한 것) 계약: `FactToken['kind']`에 `'BUYER_NAME'`·`'SELLER_NAME'`이 생겼다 → 토큰 `⟦BUYER_NAME_1⟧`·`⟦SELLER_NAME_1⟧` (지금 토큰 문법 그대로). 값은 `config/rules.json`의 `reply.names` (타입 `ReplyNames`): 서명 "Hannah, Fernwood Knits", 서연 B01 = en "Seo-yeon" · ko "서연 님", 지호 B02 = "Ji-ho" · "지호 님".
- (T056이 한 것) 토큰 종류·프롬프트(이름 값이 AI에 가지 않음)·호칭 겹침 검사. **이 작업이 할 것**: 서버에서 `nameFactsPair`로 초안용(en)·전송본용(구매자 언어) 이름 사실값을 만들어 `draftReply`·`translateReply`의 `facts`와 채우기·전송 경로에 넘긴다 (전송 경로 `src/app/_server/send.ts`도 같은 값을 다시 계산한다 — 브라우저에서 받지 않는다).
- 값 채우기: 영어 글은 `en` 꼴, 한국어 전송본은 `ko` 꼴 (전송본 언어의 꼴. 그 언어 꼴이 없으면 이름 토큰을 만들지 않는다). 구매자 ID는 시드 연결(`load.ts`가 이미 아는 구매자)에서. 표에 없는 구매자(buyer_m 등)는 `⟦BUYER_NAME_1⟧`을 만들지 않고 이름 없는 인사말 ("Hello,"). 서명 토큰은 언제나 있다.
- 호칭 겹침("⟦BUYER_NAME_1⟧ 님")은 T056이 검사 실패로 막는다. 화면은 그 사유를 다른 검사 실패처럼 보이고 보내기를 끈다 (문구는 `case.` 키).
- 서명·이름 값은 설정에서만 읽는다. 화면 코드·프롬프트에 "Hannah"·"Seo-yeon"·"서연"을 직접 쓰지 않는다 (테스트 데이터 제외).

### 3. 판매자 화면의 미리보기는 실제 값으로
- 코칭 줄, 영어 초안, 한국어 전송본 미리보기, 역번역에 남은 `{{offerAmount}}`·`{{refundAmount}}`·`{{disputeAmount}}`·`⟦DATE_1⟧`·이름 토큰 등을 **화면에서는 실제 값으로 채워** 보인다.
- **보내는 글 미리보기(영어 초안·한국어 전송본)는 실제로 나갈 글자와 똑같아야 한다** — 전송 경로가 쓰는 것과 같은 채우기 함수(사실값 토큰 채우기 + 실행 층의 금액 꼴)를 쓴다. 코칭 줄은 안내문이므로 화면 표시 규칙(달러 반올림 `toDollarsRounded`)을 따라도 된다.
- 보내는 본문 처리(토큰 검사 → 실행 층이 채움)는 바꾸지 않는다. 브라우저로 보내는 것은 지금처럼 분쟁 ID·답장 번호·확인 범주뿐이고 서버가 다시 계산한다.
- 채운 값은 눈에 띄게(예: 밑줄 점선 + 읽기용 "filled by code") 표시해도 된다 — 새 색은 만들지 않는다.

### 4. 지호 화면: 주 버튼 "Send offer · $7"
- `offerComesFirst`가 참인 분쟁(지호)은 주 버튼이 **"Send offer · $7"** — 금액은 엔진 제안 금액(`recommend(...)`의 제안 금액을 옮긴다), 표시는 달러 반올림. 화면 코드에 `7`·`700` 같은 금액을 쓰지 않는다.
- 누르면 서버가 `planMove`로 `make_offer` 계획을 만들고, 지금의 한국어 전송본을 **제안 메모(`note`)** 로 함께 보낸다 (`src/exec/request.ts`가 이미 그렇게 만든다. 호출 1회, send-message 없음). 답장 초안은 `move: 'offer'`로 만든다 (제안 금액은 `{{offerAmount}}` 자리표시자. 그때 환불은 정책 밖 약속이 아니다 — T053 규칙).
- **"Send in Korean"(메시지 보내기)는 지금처럼 꺼 두고 안내 유지.**
- 제안 버튼도 서연의 보내기와 **같은 관문**을 모두 지난다: 전송 스위치(`AFTERLOOP_REAL_SEND`가 정확히 "1"일 때만 실제, 아니면 "Simulated send"), 연결 표 `showOnScreen`·`liveSendAllowed`, 판매자 승인, 중복 방지(같은 계획은 한 번), 토큰·약속 검사, 이미 판매자 글이 있는 분쟁 막기. 추가: PayPal 상태가 `WAITING_FOR_SELLER_RESPONSE`가 아니면 제안 버튼을 끄고 이유를 보인다 (make-offer는 그 상태에서만 된다 — 실제 확인한 사실).
- 결과 표시는 서연의 보내기 결과와 같은 자리·같은 모양.
