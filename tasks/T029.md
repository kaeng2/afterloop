> **비밀값 규칙**: 이 worktree 루트에 사람이 입력한 `.env`가 있다. 어떤 방법으로도 열거나 내용·일부를 출력하지 않는다 (잠금으로도 막혀 있다. 막힌다고 다른 방법을 찾지 않는다). 스크립트가 런타임에 읽는 것만 허용된다. 출력·로그·보고서·manifest·링크 파일·에러 문구에 Client ID 일부, Secret, 액세스 토큰, Authorization 헤더가 들어가지 않게 한다. 스크립트 실행은 `npm run`으로만 한다. `PAYPAL_BASE_URL`을 다른 값으로 바꿔 실행해 보지 않는다 (샌드박스 외 주소 거부는 단위 테스트로 확인한다).

## 수정 가능 폴더
- `scripts/sandbox/` (새 파일 `disputes-read.ts` 등, 그리고 아래 4번의 `setup.ts`·`setup-steps.ts` 수정)
- `scripts/create-sandbox-orders.ts` (아래 2·3번의 옵션 추가)
- `tests/unit/sandbox-*.test.ts`
- `tests/sandbox/last-run.md` (스크립트 출력), `package.json`의 `scripts`에 `"sandbox:disputes"` 한 줄 추가만

이 밖은 수정하지 않는다. 특히 `src/` (읽기만: `@/paypal/client`, `@/paypal/disputes`, `@/paypal/mapper`), `tests/acceptance/`, `seed/`, `config/`. `tests/sandbox/manifest.json`과 `reports/sandbox-approve-links.md`는 **이번에 바꾸지 않는다** (지금 있는 주문 12건과 링크를 그대로 둔다).

## 만들 것
### 1. `npm run sandbox:disputes` — 실제 분쟁 목록 읽기 (조회만)
- `createPayPalClient` + `listDisputes` + (건별) `getDispute` + `toBoardState`를 실제 샌드박스에 대고 돌린다 (T003의 함수를 그대로 쓴다. 변환을 다시 구현하지 않는다)
- 출력: 분쟁 수, 건마다 `disputeId`·`reason`·`stage`·`channel`·`amountCents`·`dueDate`·`allowedMoves` 한 줄. **구매자 이름·이메일·주소·메시지 원문은 출력하지 않는다**
- 분쟁이 0건이면 "0 disputes (empty list)"를 출력하고 종료 코드 0. 변환할 수 없는 분쟁이 있으면 그 건의 ID와 어떤 필드가 문제인지(값은 싣지 않는다)를 출력하고 나머지는 계속, 종료 코드 1
- 결과 요약을 `tests/sandbox/last-run.md`에 "분쟁 읽기" 절로 덧붙인다
- **이번에 실행한다** (한 번). 분쟁이 아직 접수되지 않았으니 0건이 정상이다. 0건이 아니면 건수와 위 필드를 그대로 보고한다

### 2. `npm run sandbox:orders -- --status` — 주문 12건의 지금 상태 (조회만)
- manifest의 주문마다 `GET /v2/checkout/orders/{id}`로 `status`(CREATED / PAYER_ACTION_REQUIRED / APPROVED / COMPLETED 등)를 읽어 표로 출력한다. 404·만료로 보이는 응답은 "expired or not found"로 적는다. 아무것도 만들거나 바꾸지 않는다
- **이번에 실행한다** (한 번). 결과를 보고서에 적는다

### 3. `npm run sandbox:orders -- --fresh` — 링크가 만료됐을 때 새로 만들기 (코드만, **실행하지 않는다**)
- 지금 스크립트는 요청 ID가 주문 키 기준(`afterloop-order-O01`)이라 다시 실행하면 PayPal이 같은(만료됐을 수 있는) 주문을 돌려준다. `--fresh`는 요청 ID에 실행 시각 기반의 접미사(예: `afterloop-order-O01-r<YYYYMMDDHHmm>`. 시각은 스크립트 진입점에서 한 번만 읽어 주입한다)를 붙여 12건을 **새로** 만들고, manifest의 `orderId`와 링크 파일을 새 값으로 바꾼다. 이전 주문 ID는 manifest의 선택 필드(예: `previousOrderIds`)나 보고서에 남긴다. 이미 `COMPLETED`(캡처됨)인 주문은 새로 만들지 않고 그대로 둔다
- 가짜 클라이언트 단위 테스트: 새 요청 ID, 캡처된 주문 보존, 링크 파일·manifest 갱신, 접미사가 같으면 재실행해도 중복 생성 없음
- **실행하지 않는 이유**: 지금 있는 링크를 아침에 사람이 쓴다. 만료됐을 때만 컨트롤 타워가 실행한다

### 4. `setup`의 `disputes` 단계 고치기 (T001 1단계 검증 `reports/T001-verify.md`)
- 다시 실행될 때 이번에 찾은 것만으로 `manifest.disputes`를 통째로 바꾸는 문제: 이미 적힌 항목은 유지하고 찾은 것만 더하거나 갱신한다. 마지막에 D1·D2·D3이 모두 있는지 확인하고 모자라면 모자란 키를 알리고 종료 코드 1
- 단위 테스트 추가 (한 건 조회 실패 시 기존 항목 보존). **실행하지 않는다** (분쟁 접수 전)
