## 목표 (원문 9장, SPEC v2.1 8장)
`simulate(input, params?, rules?)` → `SimResult` (`SimulateFn`, `@/types` 7부). 남은 재고로 미래 `futures`(500)개를 '지금 그대로'와 '처방 적용'으로 **같은 난수**에 두 번 돌려 평균·P10~P90·평균 분쟁 수·손실 분포·처방별 폭포를 낸다. 모든 화면의 예상 손실은 이 함수 하나에서 나온다.

## 입력 / 출력 타입
- 입력: `SimInput` (`sku`, `priceCents`, `stock`, `rates`, `fixes`, `futures`, `seed`), `ParamsConfig`(안 넘기면 `config/params.json`), `PolicyConfig`(안 넘기면 `config/rules.json`)
- 출력: `SimResult` (`before`, `after`, `histogram`, `waterfall`)
- 공개 함수: `src/engine/sim.ts`의 `export const simulate: SimulateFn`
- 편의 함수: `export function simInputFor(sku, product, fixes, config?)` — 상품(가격·재고)과 `config.productRates[sku]`로 `SimInput`을 만든다. `seed`는 SKU 문자열에서 결정적으로 만든다 (예: FNV-1a 해시). 화면과 S1 합계가 같은 입력을 쓰게 하기 위한 것

## 동작
1. **난수**: 시드 고정 PRNG (예: mulberry32). `Math.random`, `Date`, `performance.now` 금지. 미래 f, 주문 i마다 난수를 **고정된 순서와 개수**로 뽑는다: 세부 유형 판정용 1개씩(유형 순서는 `SUBTYPES` 고정 순서 A1…F2 중 `rates`에 있는 것), 대응 결과용 2개 (습관 선택, 승패). 분쟁이 나든 안 나든 같은 개수를 소비해서 Before·After·폭포 단계가 **같은 난수**를 쓴다 (common random numbers)
2. **분쟁 발생**: 주문마다 유형 순서대로 `난수 < 기본 확률 × 처방 배수`이면 그 유형의 분쟁 (주문당 최대 1건, 첫 번째로 걸린 유형). 배수는 켠 처방들의 `fixes[fix].value.rateMultiplier[subtype]`의 곱
3. **분쟁 1건의 손실** (센트 정수):
   - p_win: 유형별 `params.pWin`. `tracking_24h`가 켜져 있으면 `fixes.tracking_24h.value.pWinOverride`에 있는 유형은 그 값
   - **지금 습관** (`settle_first` 꺼짐): 난수 < `habitRefundShare`(0.5)면 전액 환불 = A + t, 아니면 다투기 = 승패 난수 < p_win이면 t, 아니면 A + f + t
   - **합의 우선** (`settle_first` 켜짐): T004와 같은 기준으로 기대 손실이 가장 작은 수를 고르고(제안은 B1·B2만, 동점 fight → offer → refund), 그 수의 결과를 난수로 실현한다 — fight: 승패 난수, offer: 수락 난수 < p_acc면 x·A(센트 반올림) + t, 거절이면 승패 난수로 t 또는 A + f + t, refund: A + t. 기대 손실 계산은 `oracle.ts`의 함수를 그대로 쓴다 (식을 다시 쓰지 않는다)
   - A = `priceCents`. f, t, x, p_acc는 `params`에서
4. **요약**: 미래별 손실 합 → `meanLossCents`(반올림 정수), `p10LossCents`·`p90LossCents`(정렬 후 분위수, 방법을 주석에 명시), `meanDisputes`(소수 둘째 자리까지)
5. **`before`** = 처방 없음, **`after`** = `input.fixes` 전부 적용
6. **`waterfall`**: `as_is`부터 시작해 처방을 고정 순서(`tracking_24h` → `color_note` → `kr_customs_notice` → `settle_first`)로 `input.fixes`에 있는 것만 하나씩 더한 평균 손실. 마지막 단계 = `after.meanLossCents`
7. **`histogram`**: 미래별 손실을 구간으로 나눈 빈도. 구간 폭은 가격에 맞춰 결정적으로 정하고(예: 10개 내외 구간), Before·After가 같은 구간을 쓴다. 각 열의 합 = `futures`
8. 검증 (zod): `stock`·`futures`는 0 이상 정수, 확률 0~1, 모르는 처방 ID 거부. `stock: 0`이면 손실 0
9. 성능: 가디건(재고 120, 500개 미래) 한 번에 50ms 이내 (처방 토글 후 0.5초 재계산, 원문 F4)
10. 입력을 바꾸지 않는다. 같은 입력이면 항상 같은 결과

## 같이 고칠 것 (T018 검증 보고 `reports/T018-verify.md`)
`planMove`에 넘겨받은 평가가 `expectedLossCents: null`인데 `blockedBy`가 없으면(손으로 만든 평가) 지금은 계획이 나온다. **넘겨받은 평가의** `expectedLossCents`가 `null`이면 계획을 만들기 전에 예외를 던진다. 값의 크기는 대조하지 않는다 (AC4가 제안률 0.15로 만든 평가를 0.20으로 계획하므로). AC4·AC10과 정상 입력의 계획·`planId`는 그대로여야 한다. 단위 테스트 1~2개 추가

## 완료 기준 (단위 테스트)
- [ ] 결정론: 같은 입력 100회 같은 결과, `Math.random`·`Date.now` 미호출 (spy)
- [ ] 같은 난수: 처방을 켜도 분쟁이 **새로 생기지 않는다** (배수 ≤ 1이므로 After의 분쟁 주문 집합 ⊆ Before). 미래별로 확인
- [ ] 단조성: 4개 상품 모두 `waterfall`이 단계마다 늘지 않는다 (같은 난수라 성립해야 한다. 성립하지 않는 단계가 있으면 이유와 함께 보고)
- [ ] 통계 건전성: Before `meanDisputes` ≈ 재고 × Σ확률 (가디건 120 × 3.6% ≈ 4.3, 허용 오차 ±0.4), Before 평균 손실이 "분쟁 수 × 분쟁당 기대 손실(습관)"의 손 계산과 ±10% 안
- [ ] 폭포 마지막 = `after`, 히스토그램 열 합 = 500, 요약 값은 정수 센트
- [ ] 경계: 재고 0, 확률 전부 0, 처방 없음(`before` = `after`), 처방 순서를 바꿔 넣어도 같은 결과
- [ ] 성능 50ms 이내 (여유 있게 측정)
- [ ] **보고서에 숫자 표**: 4개 상품(`config/params.json`의 `productRates`, 가격·재고는 `seed/products.json`을 읽기만) × Before/After(처방 4개)의 평균·P10·P90·평균 분쟁 수, 그리고 4개 상품 합계(상품별 달러 반올림 후 합산). 원문 값(가디건 $195 → $43, 합계 $481 → $143)과 나란히 적는다. **원문 값에 맞추려고 난수·시드·식을 조정하지 않는다**
- [ ] 인수 테스트 **AC22** (작성 후) 통과
- [ ] `npx tsc --noEmit`에서 자기 파일 오류 없음, T004·T005·T018 인수 테스트 그대로 통과
