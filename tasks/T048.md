> **가장 중요한 규칙**
> 1. **기존 `simulate`의 결과는 한 숫자도 바뀌지 않는다.** `tests/unit/sim.test.ts`의 기대값을 한 글자도 고치지 않고 통과해야 한다. 난수를 뽑는 순서·개수도 바꾸지 않는다.
> 2. 합계와 "대표 미래"는 **엔진 안에서만** 계산한다. 화면은 옮기기만 한다. 엔진은 **센트 정수만** 돌려준다 (달러 반올림은 화면의 `toDollarsRounded` 한 곳).
> 3. `Math.random`·`Date`·`performance.now`를 쓰지 않는다. 같은 입력이면 항상 같은 결과.
> 4. `.env`를 찾지 않는다. 실제 PayPal·LLM 호출을 하지 않는다.

## 배경
- S1(Today)은 "가게 전체 예상 손실 전 → 후" 한 쌍이 필요하다. 지금 `simulate`는 상품 하나만 계산한다. 화면이 더하면 "숫자 계산은 엔진에서만" 규칙이 깨진다.
- S2(Product check)의 주인공은 점 그림이다: 주문 하나 = 점 하나, 분쟁 난 주문 = 빨간 점. 왼쪽(지금 그대로) / 오른쪽(처방 적용)에서 "빨간 점 4개 → 2개"처럼 줄어드는 모습을 보여 준다. 500개 미래 중 **어느 미래를 그릴지** 화면이 정하면 안 된다.
- 이미 있는 것: `simulatePass(input, fixes, params?, rules?)`는 미래별 `lossCents`·`disputes`·`disputeOrders`를 돌려준다. 다만 분쟁 난 **세부 유형**은 담지 않는다.

- 지금까지 문서에 적힌 $718 → $254는 상품별로 반올림한 달러를 더한 값이었다. **정본은 센트 합이다** (71718¢ → 25316¢, 표시 $717 → $253). 상품별 행의 합과 $1 다를 수 있는 것은 화면이 다룬다 ("합계는 행의 합과 $1까지 다를 수 있다"). 엔진은 관여하지 않는다.

## 직접 계산해 둔 값 (초안 작성 시, 구현이 이 값을 낼 때 맞는지 확인용)
`simInputFor(sku, product, [...FIX_ORDER])`로 시드 상품 4개를 돌린 결과 (처방 4개 모두 켬):

| 상품 | 평균 손실 전 | 후 (센트) | 평균 분쟁 전 → 후 |
|---|---|---|---|
| FK-CD-OAT (가디건) | 21619 | 4366 | 4.46 → 2.07 |
| FK-SW-NV | 10988 | 2562 | 1.59 → 0.76 |
| FK-CT-GR | 13651 | 11310 | 0.75 → 0.66 |
| FK-BN-SET | 25460 | 7078 | 6.31 → 5.69 |

- **센트로 더하면 71718 → 25316 → 표시 `$717` → `$253`.**
- 상품별로 먼저 달러 반올림해 더하면 216+110+137+255 = 718, 44+26+113+71 = 254 → `$718` → `$254`. 화면 초안(T014·T016)이 적은 "$718 → $254"는 이 두 번째 방식에서 나온 값이다.
- 즉 어느 반올림 순서를 쓰느냐로 $1씩 다르다. 아래 규칙으로 하나만 쓴다.

## 정할 규칙

### 1. 합계는 센트 정수의 합 (확정)
- `전체 전 = Σ 상품별 before.meanLossCents`, `전체 후 = Σ 상품별 after.meanLossCents` (둘 다 상품별 `simulate`가 이미 센트 정수로 돌려준 값을 정수 덧셈만 한다. 합계에서 다시 반올림하지 않는다).
- P10·P90은 합계에 넣지 않는다 (분위수는 더할 수 없다). 합계에 쓰는 것은 평균 손실과 평균 분쟁 수(소수 둘째 자리 값을 더하지 않고, 필요하면 상품별 값을 그대로 돌려준다)뿐.
- 표시 반올림은 화면의 `toDollarsRounded(totalCents)` **한 번**. 결과: 이 시드·현재 가정값에서 `$717 → $253`.
- 결정됨 (컨트롤 타워): 센트 합이 정본이다. 행 합과 $1 어긋나는 것은 화면 몫이고 엔진은 두 번째 반올림 방식을 만들지 않는다.
- S1이 켜는 처방: **처방 4개를 모두 켠 값이 "After"다** (SPEC 8장). `simulateStore`는 넘어온 `fixes`를 모든 상품에 똑같이 쓰고, S1은 `[...FIX_ORDER]`를 넘긴다. 다른 조합은 S2 화면이 `simulate`를 직접 부른다.

### 2. 상품별 결과와 순서
- 상품별 결과를 함께 돌려준다 (`simulate`의 `SimResult` 그대로).
- **정렬: `before.meanLossCents` 큰 순서. 같으면 입력으로 들어온 순서(= 시드 `products.json` 순서)대로.** 안정 정렬을 쓴다.
- 사람 결정: 첫 화면 순서는 **엔진 계산 순서 그대로**다. 지금 값이면 FK-BN-SET(비니 세트) 25460이 1위, 그다음 FK-CD-OAT 21619, FK-CT-GR 13651, FK-SW-NV 10988이다. 비니 세트가 1위여도 화면이 순서를 바꾸지 않는다. 엔진도 다른 기준(예: 줄어드는 폭)으로 다시 정렬하지 않는다.

### 3. 점 그림용 "대표 미래" 고르기
- **규칙: Before 패스의 평균 분쟁 수(소수 그대로, 반올림 안 함)에 분쟁 수가 가장 가까운 미래. 거리가 같으면 미래 번호가 가장 작은 것.**
  - 평균은 `Σ disputes / futures`. 거리는 `|분쟁 수 − 평균|`. 부동소수점 비교가 흔들리지 않게 `분쟁 수 × futures`와 `Σ disputes`의 정수 차이로 비교한다.
- 고르는 데는 **Before 패스만** 쓴다. 처방을 켜고 끄거나 `fixes`를 바꿔도 같은 미래가 뽑힌다 (토글할 때 점 위치가 뛰지 않는다). `fixes`가 달라지는 것은 오른쪽(After) 그림뿐.
- Before와 After는 **같은 미래 번호**를 쓴다 (같은 난수, SPEC 8장). 같은 주문 번호의 점이 양쪽에 있고, 오른쪽 빨간 점은 왼쪽 빨간 점의 일부다 (처방 배수 ≤ 1이라 After의 분쟁 주문 ⊆ Before).
- 직접 계산해 둔 값 (확인용): FK-CD-OAT는 평균 4.458 → 미래 1번, 분쟁 전 4건 → 후 2건 (리뷰 문구 "빨간 점 4개 → 2개"와 맞는다). FK-SW-NV 평균 1.588 → 0번, 2 → 1. FK-CT-GR 평균 0.746 → 1번, 1 → 1. FK-BN-SET 평균 6.312 → 5번, 6 → 6.

### 4. 돌려줄 것 (엔진 파일이 export. 계약 `src/types.ts`는 바꾸지 않는다)
`src/engine/sim.ts`는 이미 `SimPass`를 export한다. 아래는 같은 폴더의 **새 파일** `src/engine/storefront.ts`에 둔다 (`sim.ts`는 아래 "고칠 곳"의 최소 변경만).

```ts
// 가게 합계
type StoreProductResult = { sku: string; result: SimResult };       // simulate 결과 그대로
type StoreTotal = {
  beforeCents: number;                                               // Σ before.meanLossCents
  afterCents: number;                                                // Σ after.meanLossCents
  products: StoreProductResult[];                                    // 정렬 규칙 적용 후
};
simulateStore(products: { sku; priceCents; stock }[], fixes: FixId[], params?, rules?): StoreTotal

// 점 그림용 대표 미래
type DotOrder = {
  index: number;                    // 주문 번호 0..stock-1
  disputedBefore: boolean;
  disputedAfter: boolean;           // 항상 disputedBefore 이상으로만 참 (참이면 Before도 참)
  subtypeBefore: Subtype | null;    // 분쟁 난 세부 유형
  subtypeAfter: Subtype | null;
};
type RepresentativeFuture = {
  futureIndex: number;              // Before·After가 함께 쓰는 미래 번호
  orders: DotOrder[];               // 길이 = stock, 번호 순
  disputesBefore: number;
  disputesAfter: number;
};
pickRepresentativeFuture(input: SimInput, params?, rules?): RepresentativeFuture
```
- 이름은 제안이다. 구현이 더 나은 이름을 고르면 보고서에 적는다. 화면이 부를 이름이 정해진 뒤에는 바꾸지 않는다 (T013·T014 지시서가 이 이름을 가리킨다).
- `pickRepresentativeFuture`는 `input.fixes`를 After에 쓴다. `input.fixes`가 빈 배열이면 After = Before (`disputedAfter === disputedBefore`).
- 세부 유형은 주문마다 "유형 판정 난수" 순서(`SUBTYPES` 고정 순서)에서 처음 걸린 유형이다. **처방을 켜면 확률이 줄어 같은 주문이 다른 유형으로 걸릴 수도 있다** (앞 유형은 빠지고 뒤 유형이 남는 경우). 그래서 After의 유형을 따로 돌려준다. 이 경우를 테스트로 확인하고, 안 생기면 안 생긴다고 보고서에 적는다.

### 고칠 곳 (기존 코드를 건드리는 최소선)
- `src/engine/sim.ts`: `runPass`가 분쟁 난 주문의 **유형**도 기록하도록 `SimPass`에 칸 하나를 더한다 (예: `disputeSubtypes: Subtype[][]`, `disputeOrders`와 같은 모양). 난수를 뽑는 순서·개수·비교는 그대로. `simulate`의 반환값에는 이 칸을 넣지 않는다 (결과가 바뀌면 안 된다).
- 그 밖의 엔진 파일(`oracle.ts`, `policy.ts`, `params.ts`, `rng.ts`)과 `config/`는 수정하지 않는다.
