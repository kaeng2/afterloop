## 만들 것
### `.env.example`
`PAYPAL_CLIENT_ID=`, `PAYPAL_CLIENT_SECRET=`, `PAYPAL_BASE_URL=`, `LLM_API_KEY=` (값은 비움). 각 키를 어디서 받는지 한 줄 주석.

### `scripts/sandbox/setup.ts` (`npm run sandbox:setup -- <단계>`)
> 2026-11-09: `orders`·`capture` 단계는 **T026**(`scripts/create-sandbox-orders.ts`, `scripts/capture-sandbox-orders.ts`)이 대신한다. 이 작업에서는 `track`·`disputes`와 `check.ts`, `.env.example`만 만든다. 승인은 브라우저 에이전트가 한다.

| 단계 | 하는 일 |
|---|---|
| `orders` | Orders v2로 주문 12건 생성. `purchase_units[].items[].name`에 상품명(원문 6-1), 금액은 상품 가격. 구매자별 승인 링크 출력 |
| `capture` | 승인된 주문을 캡처. 캡처 ID를 manifest에 기록 |
| `track` | 아래 표의 "추적" 7건에 Orders v2 `POST /v2/checkout/orders/{id}/track` 1회씩 (가상 추적번호, carrier OTHER) |
| `disputes` | `GET /v1/customer/disputes`에서 manifest 캡처에 걸린 분쟁을 찾아 D1~D3 ID를 manifest에 기록 |

- 각 단계는 다시 실행해도 안전해야 한다 (이미 된 주문은 건너뜀, `PayPal-Request-Id`는 주문 키 기준).
- **요청 ID 길이 확인** (2026-11-09 결정, 1단계에서 한다): 실행 계획의 요청 ID는 약 61자다 (`plan-<분쟁 ID>-<수>-<API>-<금액>-<환불 종류>:<엔드포인트>`). 아직 주문이 없어 `track`으로는 확인할 수 없으므로, `npm run sandbox:check -- --probe-request-id`를 만든다: **61자 `PayPal-Request-Id`로 `POST /v2/checkout/orders` 1건**(intent CAPTURE, USD 1.00, 상품명 `Request-Id length probe`)을 보내 상태 코드를 본다. 그 주문은 승인·캡처하지 않고 manifest에도 넣지 않는다 (버려지는 주문). 같은 ID로 한 번 더 보내 같은 주문 ID가 돌아오는지(멱등)도 본다. 비교용으로 36자 ID 1건도 보낸다. 결과(ID 길이, 상태 코드, 거부면 오류 `name`·`issue`)를 `tests/sandbox/last-run.md`와 보고서에 적는다. Orders API에서의 확인이고, 분쟁 API(send-message 등)는 첫 실호출(T009) 때 다시 확인한다

### `scripts/sandbox/check.ts` (`npm run sandbox:check`, `--json`)
조회만 한다. `.env`는 스크립트가 직접 읽는다 (`process.loadEnvFile`. 이미 환경 변수에 있으면 그대로).
1. 토큰 발급
2. 기능 확인: `GET /v1/customer/disputes?page_size=1` 상태 코드, `GET /v1/reporting/transactions`(최근 30일) 상태 코드
3. manifest 주문마다 `GET /v2/checkout/orders/{id}`: 상태, 상품명, `payer.payer_id`, `payer.address.country_code`, 캡처 ID, 추적 등록 여부
4. manifest 분쟁마다 `GET /v1/customer/disputes/{id}`: reason, `dispute_life_cycle_stage`, status, `disputed_transactions[].seller_transaction_id`

`--json`은 한 줄만 출력한다 (AC13이 읽는 형식):
```json
{ "token": { "ok": true },
  "features": { "disputes": 200, "transactionSearch": 200 },
  "orders": [{ "key": "O01", "orderId": "...", "status": "COMPLETED", "itemNames": ["Wool Sweater, Navy"], "payerId": "...", "payerCountry": "US", "captureId": "...", "tracked": true }],
  "disputes": [{ "key": "D2", "disputeId": "...", "reason": "MERCHANDISE_OR_SERVICE_NOT_RECEIVED", "stage": "INQUIRY", "status": "WAITING_FOR_SELLER_RESPONSE", "captureIds": ["..."] }] }
```
결과 요약(엔드포인트, 상태 코드, 주문·분쟁 ID, 시각)을 `tests/sandbox/last-run.md`에 덮어쓴다. `PAYPAL_BASE_URL`이 샌드박스가 아니면 호출하지 않고 종료 코드 1.

~~이 단계에서는 `fetch`를 직접 쓴다 (클라이언트 교체는 T003).~~ `createPayPalClient`를 쓴다 (맨 위 갱신 참고). path는 `/`로 시작하는 상대 경로, 쿼리 값은 퍼센트 인코딩.

manifest가 비어 있으면(1단계) 주문·분쟁 확인은 건너뛰고 `orders: []`, `disputes: []`로 보고한다 (오류로 끝내지 않는다). 기능 확인이 403이면 "기능 반영 대기일 수 있음 (최대 10분)"이라고 적고 종료 코드 0이 아닌 값으로 끝낸다.
