> **가장 중요한 규칙 — 안전 규칙 (SPEC 9-3)**
> 1. **열린 분쟁이 있는 주문에는 추적번호를 등록하지 않는다.** 연습용 분쟁과 시연 제외 분쟁이 걸린 주문도 포함한다. 일괄 등록 목록에서 자동으로 빼고, 화면에는 "분쟁 진행 중이라 제외"로 보인다. 이유: 추적번호가 등록된 주문의 미수령 분쟁 2건이 접수 직후 PayPal 심사로 넘어갔다. 서연(O13)·지호(O02) 분쟁이 심사로 넘어가면 시연을 할 수 없다.
> 2. 이 판정은 **두 군데**에서 한다: 화면(고를 수 없게)과 서버(화면이 보낸 목록에 섞여 와도 호출 전에 뺀다).
> 3. 추적 등록은 되돌릴 수 없다. **이 작업 중에는 실제 PayPal 호출을 한 번도 하지 않는다** (가짜 클라이언트로만 시험). 실호출 시험은 병합 뒤 컨트롤 타워가 **O03 한 건으로만** 한다. **O05·O07은 녹화용이다 — 어떤 시험에도 쓰지 않는다.**
> 4. `/v1/shipping/trackers*`는 쓰지 않는다 (지원 중단, 이 앱에서 403). 주문별 `POST /v2/checkout/orders/{id}/track`만.
> 5. 화면은 계산하지 않는다. 건수는 행을 세고, 나머지는 서버 함수 결과를 옮긴다. `.env`를 찾거나 만들지 않는다.

### 실제 등록 스위치
- 기본은 가짜 등록이다 (네트워크를 타지 않는 클라이언트. 결과 표시는 "Simulated — nothing was sent to PayPal").
- 실제 등록은 명시적인 환경 변수를 켰을 때만 (이름은 사람 확인 필요. T009의 전송 스위치와 따로 둔다 — 하나를 켠다고 다른 것이 켜지면 안 된다).
- 서버 액션은 받은 주문 목록에서 **분쟁 걸린 주문을 호출 전에 다시 뺀다.** 뺀 주문은 결과에 `excluded`로 돌려준다.
- 누르면 바로 버튼이 꺼진다. 이미 등록된 주문은 다시 보내지 않는다 (T011이 주문 상세로 확인).

## 보기용 데이터를 만드는 순수 함수 (`src/app/orders/model.ts`)
DOM·네트워크·시계·난수를 쓰지 않는다. 인수 테스트(AC28)가 직접 부른다.

- `buildOrderRows(input)` → 행 배열. `input`: `{ orders: { key, buyerId, sku, amountCents, hasTracking }[], disputedOrderKeys: string[], buyers, products }`. 행마다 `{ key, …, state: 'untracked' | 'tracked', excluded: boolean, selectable: boolean, badges }`.
- `selectableKeys(rows)` → 고를 수 있는 주문 키. **S1(T014)도 이 함수를 부른다.**
- `buildTrackRequest(rows, selectedKeys)` → 서버로 보낼 주문 키. **제외·등록됨 행은 넣어도 빠진다.**
- `buildTrackSummary(results)` → `{ added, failed, excluded, statusCodes, lines }` (세기만 한다).
- `openDisputeOrderKeys(disputeLinks)` → 분쟁이 가리키는 주문 키 (**연습용·시연 제외 분쟁 포함**).
