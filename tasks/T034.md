# T034: 주문 생성 본문에 승인 뒤 돌아갈 주소 추가

| 항목 | 값 |
|---|---|
| 기준 SPEC | v2.2 (시작할 때 `SPEC.md` 첫 줄과 비교. 다르면 작업하지 말고 보고) |
| 레인 | paypal |
| 브랜치 / worktree | `lane/paypal` / `../afterloop-wt/paypal` (`.env` 있음) |
| 예상 시간 | 30분 |
| 의존 | T026, T029, T030 (이 브랜치에 있음) |
| 출처 | 사람 보고 2026-11-10: 결제 승인 화면에서 마지막 버튼("주문 검토로 계속" / "Review Order")을 누르면 같은 화면만 새로고침되거나 로딩만 계속됐다. 주문 생성 요청에 승인 뒤 돌아갈 주소가 없었다 (`buildOrderBody`에 `return_url`·`cancel_url` 없음). 승인 자체는 PayPal 쪽에서 완료되어 12건 모두 `APPROVED` → 캡처까지 끝났다 |

> **가장 중요한 규칙**
> 1. 이 worktree 루트에 사람이 입력한 `.env`가 있다. 어떤 방법으로도 열거나 내용·일부를 출력하지 않는다 (잠금으로도 막혀 있다).
> 2. **이 작업은 실제 PayPal 호출을 한 번도 하지 않는다.** `npm run sandbox:*`를 어떤 옵션으로도 실행하지 않는다. **지금 주문 12건은 캡처가 끝난 상태다 (`tests/sandbox/manifest.json`에 `captureId` 12개).** 가짜 클라이언트 단위 테스트만 한다.
> 3. `tests/sandbox/manifest.json`, `reports/sandbox-approve-links.md`, `reports/sandbox-capture-first-run.md`는 한 글자도 바꾸지 않는다.

## 수정 가능 폴더
- `scripts/create-sandbox-orders.ts` (필요하면 `scripts/sandbox/`의 공용 모듈)
- `tests/unit/sandbox-orders.test.ts`, `tests/unit/sandbox-orders-protect.test.ts`

이 밖은 수정하지 않는다. 특히 `scripts/capture-sandbox-orders.ts`, `src/`, `tests/acceptance/`, `seed/`, `config/`, `package.json`.

## 고칠 것
1. **주문 생성 본문에 `payment_source.paypal.experience_context` 추가** (`buildOrderBody`):
   - `return_url: 'https://example.com/afterloop/return'`
   - `cancel_url: 'https://example.com/afterloop/cancel'`
   - `user_action: 'PAY_NOW'`
   - **배송지는 기본값 유지**: `shipping_preference`를 넣지 않는다 (`NO_SHIPPING`으로 바꾸지 않는다. 배송 추적과 미수령 분쟁에 배송지가 필요하다)
   - 두 주소는 이름 붙인 상수로 둔다. 그 밖의 본문(`intent: 'CAPTURE'`, `purchase_units`, 상품명, 금액, `item_total` 내역)은 그대로
2. **승인 링크의 `rel`**: `payment_source`를 넣으면 응답의 주문 상태가 `PAYER_ACTION_REQUIRED`이고 승인 링크의 `rel`이 `approve`가 아니라 `payer-action`일 수 있다. 지금 코드가 둘 다 고르는지(`approve`, 없으면 `payer-action`) 확인하고, 둘 다 있을 때·`payer-action`만 있을 때·둘 다 없을 때를 테스트로 고정한다
3. **기존 안전장치는 그대로**: 승인 링크가 샌드박스 주소(`www.sandbox.paypal.com`)가 아니면 멈추는 검사, 샌드박스가 아닌 `PAYPAL_BASE_URL`이면 호출 0회, T030의 보호(캡처·승인된 주문을 다시 만들지 않음, `--` 빠진 옵션 막기). `return_url`·`cancel_url`은 우리가 보내는 값이지 응답의 승인 링크가 아니므로, 샌드박스 주소 검사의 대상이 아니다 (검사 대상을 헷갈려 `example.com` 때문에 멈추지 않게 한다)
4. **주문 상태 해석**: 새 주문의 상태 `PAYER_ACTION_REQUIRED`를 `--status`, `--fresh`, 캡처 스크립트가 "승인 전"으로 다루는지 확인한다 (T030에서 `CREATED`와 같이 다루도록 되어 있다. 캡처 스크립트는 수정 금지 폴더이므로 읽기만 하고, 문제가 있으면 보고서에 적는다)
5. 링크 파일 맨 위 안내에 한 줄 추가 (다음에 스크립트가 파일을 쓸 때 들어가도록 코드만): "승인하면 `https://example.com/afterloop/return?...`으로 넘어간다. 그 화면이 뜨면 승인이 끝난 것이다."

## 완료 기준 (단위 테스트, 가짜 클라이언트만)
- [ ] 12건의 요청 본문 모두에 `payment_source.paypal.experience_context.return_url`·`cancel_url`·`user_action`이 위 값으로 들어 있다. `shipping_preference`는 없다
- [ ] 응답 링크 고르기 3가지 (`approve`만 / `payer-action`만 / 둘 다) + 없음
- [ ] 응답 상태 `PAYER_ACTION_REQUIRED`인 주문이 manifest·링크 파일에 정상 기록된다
- [ ] 승인 링크가 `https://www.paypal.com/...`(live)이면 멈춘다. `return_url`이 `example.com`이어도 멈추지 않는다
- [ ] 기존 단위 테스트 통과 (요청 본문 전체를 `toEqual`로 비교하던 테스트의 기대값은 새 필드만큼 바뀌는 것이 정상. 바꾼 곳을 보고서에 적는다)
- [ ] `npm test`, `npx tsc --noEmit`(자기 파일 오류 없음), `npm run lint`
- [ ] `git diff --stat`에서 `tests/sandbox/manifest.json`·`reports/sandbox-approve-links.md`·`reports/sandbox-capture-first-run.md` 변경 0줄, 실호출 0회

- 캡처 스크립트 수정, AC13·manifest 계약 변경
