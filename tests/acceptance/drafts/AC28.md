# AC28 초안: S3 At-risk orders (T016)

**상태: 초안 (심사위원 리뷰 반영 전, 사람 승인 전).** 실행 코드가 아니라 시험 항목 목록이다. 승인 뒤 컨트롤 타워가 `tests/acceptance/ac28.orders.test.ts`로 옮긴다.

- 대상: `src/app/orders/model.ts`의 `buildOrderRows`·`selectableKeys`·`buildTrackRequest`·`buildTrackSummary`·`openDisputeOrderKeys`, `src/app/orders/actions.ts`의 등록 서버 함수 (T016이 만든다)
- 기준: SPEC v2.3 9-3장 (안전 규칙 포함)·9-5장·10장, 검토 M3, 원문 8장 S3
- **실제 호출 없음.** PayPal 클라이언트는 `get`·`call` 횟수와 경로를 적어 두는 가짜만 쓴다. 추적 등록은 되돌릴 수 없으므로 인수 테스트는 어떤 경우에도 실제로 부르지 않는다. DOM 없이 순수 함수만 부른다 (저장소에 DOM·브라우저 시험 도구가 없다)
- T011 (앱이 쓰는 추적 등록 함수)이 아직 없다. 아래 "결과" 꼴은 T016이 기대하는 것이고, T011 지시서가 나오면 맞춘다

## 확인 필요 (사람이 정한다. 기대값을 지어내지 않았다)
1. 제외 문구의 영어 문장 (제안: "Excluded — dispute in progress").
2. **추적 등록에도 "기본은 가짜" 스위치를 둘지**, 그리고 녹화용으로 미등록 주문을 몇 건 남길지. 실호출 시험에 O03·O04·O05·O07을 다 쓰면 녹화 때 누를 수 있는 주문이 0건이 된다 (10번 항목의 상태). T016 "사람이 정할 것" 1번.
3. 등록하는 추적번호가 가상 값이다 (스크립트의 `FKAL032026` 꼴). 화면 배지와 README 정직성 표에 넣을지. SPEC 10장의 시연용 데이터 4가지에는 없다.
4. 상태 코드 표기. 실제 응답은 201이었다 (`DECISIONS.md` 2026-11-10 추적번호 7건). SPEC 9-3 예시 문구는 "· 200"이다. 7번 항목은 "받은 코드 그대로"를 전제로 썼다. 성공 코드가 섞이면 (200과 201) 요약 줄에 무엇을 적을지.
5. T011이 내놓는 결과의 꼴 (`added` / `failed` / `excluded`, 상태 코드, 추적번호, 이유). T011 지시서가 정본이다.
6. 금지 문구의 영어 목록 (AC18 초안 확인 필요 3과 같다).
