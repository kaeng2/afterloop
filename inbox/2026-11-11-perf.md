# disputeless 페이지 이동 지연 원인 분석 (배포 커밋 0c4ca78 기준)

## 증상
- "Today", "Black Friday rehearsal" 탭을 클릭하면 5~7초 동안 화면이 바뀌지 않는다.
- 측정값
  - `/`: 약 5.9초
  - `/products`: 약 7.0초
  - 클라이언트 이동(RSC) 요청: 4.9~5.9초
  - `/api/health`: 0.15초 (콜드 스타트나 네트워크 문제는 아님)
- Fixes 스위치를 토글하면 메인 스레드가 70~220ms 멈춘다. 서버 요청은 없다.

## 원인

### 1. 모든 페이지 틀이 PayPal 조회가 끝날 때까지 기다림
- `src/app/layout.tsx:42`의 `await loadTodayForRequest()`
  - 최신 main(881cbb7)에서는 `src/app/(app)/layout.tsx`로 옮겨졌다.
- 상단 "Today (N)"의 숫자 N 하나 때문에 `/products`도 분쟁 조회와 주문 조회가 끝나야 렌더링된다.

### 2. 주문 8건을 순차 조회 (가장 느린 구간)
- `src/paypal/track.ts:147`의 `listUntracked`가 `for` 문 안에서 `await client.get('/v2/checkout/orders/...')`를 한 건씩 실행한다.
- 대상: O03, O05, O06, O07, O09, O10, O11, O12
- 활동 기록상 1건에 0.6~0.8초라서 합계가 약 5초다.

### 3. 분쟁 상세와 AI 판정도 순차 실행
- `src/app/_server/disputes.ts:274-276`: 분쟁 목록을 받은 뒤 상세 3건을 차례로 `await` 한다.
- `src/app/_server/disputes.ts:291~`: 분쟁마다 `buildBoard`(최대 2회)와 `judgeTone`을 차례로 `await` 한다.
- AI 응답은 `data/ai-cache/llm-cache.json`에 캐시되어 있다. 캐시에 없는 요청이면 AI 호출 시간이 그대로 더해진다 (운영 환경의 캐시 적중 여부는 미확인).
- 이 경로는 2번의 주문 조회와 `Promise.all`로 함께 돌아간다 (`src/app/_server/today.ts:38`). 따라서 전체 시간은 둘 중 느린 쪽이 정한다.

### 4. 요청 사이 캐시 없음
- `loadDemoDisputesForRequest`와 `loadTrackingForRequest`는 React `cache()`라서 요청 한 번 안에서만 결과를 재사용한다.
- 클릭할 때마다 PayPal을 처음부터 다시 조회한다.
- 매출 조회(`src/app/products/transactions-line.ts`)만 프로세스 메모리 캐시(TTL 15분)가 있다.

### 5. PayPal 클라이언트를 매번 새로 만들어 토큰을 재발급
- `src/app/_server/paypal.ts:92`의 `getPayPalClient()`는 호출할 때마다 `createPayPalClient()`를 새로 만든다.
- 토큰 재사용 로직(`src/paypal/client.ts:291`)과 속도 제한 기록(`src/paypal/client.ts:216`)이 인스턴스마다 따로 있다.
- 그래서 요청마다 `POST /v1/oauth2/token`이 2회(분쟁용, 주문용) 더 나간다. 활동 기록에는 보이지 않는다.

### 6. 로딩 UI 없음
- `loading.tsx`와 `Suspense`가 없어서 링크를 클릭해도 서버 응답이 올 때까지 화면 변화가 없다.

### 7. (작은 문제) 토글할 때마다 시뮬레이션 전체를 동기 재계산
- `src/app/products/products-screen.tsx:42-43`
- 토글마다 `simulateStore`(4개 상품 x 500개 미래), `simulate`, `fixSavings`를 메인 스레드에서 다시 계산한다.

### 참고
- 활동 서랍에 "같은 주문 6 calls"처럼 보이는 줄이 있지만 중복 조회가 아니다.
- `src/app/_shared/activity-view.ts`의 `groupRecords`가 연속된 주문 조회를 한 줄로 합치고 주문 ID 하나만 표시한다. 실제로는 서로 다른 주문 8건이다.

## 수정안 (우선순위 순)

1. **주문 조회 병렬화**
   - `listUntracked`의 `for` 문을 `Promise.all`로 바꾼다.
   - 기대 효과: 약 5초에서 0.8초 안팎으로 단축.

2. **분쟁 상세, AI 판정 병렬화**
   - `loadDemoDisputes`의 두 반복문을 `Promise.all`로 바꾼다.

3. **요청 사이 캐시 추가**
   - 분쟁 목록, 분쟁 상세, 주문 조회 결과를 모듈 수준 메모리 캐시(TTL 1~2분)에 저장한다.
   - 답장 전송, 추적 등록 같은 서버 액션 뒤에는 해당 캐시를 무효화한다.

4. **PayPal 클라이언트 싱글턴화**
   - 모듈 수준에서 한 번만 만들고 재사용해서 토큰 재발급을 없앤다.
   - 주의: 싱글턴으로 바꾸면 "60초 30회" 속도 제한도 공유된다. 캐시 없이 이것만 바꾸면 클릭 2~3번에 제한에 걸려 대기가 생기므로 반드시 3번과 함께 적용한다.

5. **레이아웃 블로킹 제거**
   - 상단 Today (N) 카운트를 `Suspense`로 분리해서 스트리밍한다.
   - `src/app/(app)/loading.tsx`를 추가해서 클릭하자마자 로딩 상태가 보이게 한다.

6. **토글 계산 지연**
   - `useDeferredValue` 또는 `startTransition`을 적용한다.
   - 또는 Web Worker로 옮기거나, 왼쪽 표는 미래 개수를 줄여서 계산한다.

- 3, 4까지 적용: 반복 클릭 약 0.3초 이하
