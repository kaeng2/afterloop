# seed/ — 데모 시드 데이터 (T007·T028·T045, data 레인)

모든 화면이 쓰는 데모 데이터다. 기준: **SPEC v2.5**, 원문(PRD v2) 6장 + 기획자 결정 2026-11-09 (Q8·Q10) + 사람 승인 2026-11-10 (배송사 데이터).

```
npm run seed    # 아래 JSON 6개를 다시 만들고 zod 검증 후 요약 출력 (DB 적재는 T025)
npm test        # tests/unit/seed.test.ts — 원문 표와 대조
```

| 파일 | 건수 | 원문 |
|---|---|---|
| `products.json` | 4 | 6-1 |
| `buyers.json` | 12 (B01~B12) | 6-2 |
| `inquiries.json` | 31 (표 8 + 자동 생성 23) | 6-3 |
| `disputes.json` | 9 (D1~D9) | 6-4 |
| `orders.json` | 214 (샌드박스 12 + 시드 202) | 4-1, 6-1, 6-5 |
| `carrier-events.json` | 7 (O01 3 + O08 4) | S5 (SPEC v2.5 12장) |

소스: `schemas.ts` (zod, `src/types.ts` 8부와 1:1) · `data.ts` (표 값 + 결정적 자동 생성) · `generate.ts` (CLI) · `index.ts` (화면·테스트용 입구).

## 규칙

- **결정적이다.** `Math.random`·`Date.now`를 쓰지 않는다. 고정 시드 난수(mulberry32)로 순서만 섞고 건수는 할당량으로, 주문일은 고정 규칙으로 못 박는다 (날짜 계산은 UTC 문자열 연산). 두 번 돌리면 바이트까지 같은 파일이 나온다 (단위 테스트가 확인).
- **LLM을 쓰지 않는다.** 자동 생성 문의는 `data.ts`의 고정 템플릿이다. 한국어는 존댓말 템플릿이고 팀이 검수한다.
- **계산하지 않는다.** 주문 금액은 원문 6-1의 상품 가격을 옮기기만 한다. 분쟁 확률·기대 손실은 engine 레인(`config/params.json`)이다. 예외는 **이미 끝난** 종결 분쟁의 손실 하나다: 결과 종류(전액 환불 / 패소 / 승소)와 상품 가격, `config/params.json`의 `params.feeCents`(읽기만)로 만든다 (아래 Q8).
- **이름은 모두 가상이다.** 이메일·주소·개인통관고유부호 값은 넣지 않는다 (단위 테스트가 확인).
- `source: 'sandbox'`는 T001이 샌드박스에 실제로 만드는 행, `source: 'seed'`는 화면에 **'Demo data' 배지**가 붙는 행이다 (SPEC 10장).

## T001(paypal 레인)과 맞물리는 부분

`orders.json`의 샌드박스 12건은 **자리표시자**다. `id`가 `O01`~`O12`이고, T001이 쓰는
`tests/sandbox/manifest.json`의 `orders[].key`와 같은 값이어야 한다 (AC13이 그 키로 조회한다).

**배정의 정본은 `tasks/T001.md`의 "주문 12건 배정" 표다.** 시드는 그 표의 키·구매자·상품·추적
여부를 행마다 그대로 옮겨 적는다 (T026의 주문 생성 스크립트도 같은 표를 따른다). 아래 표는
옮겨 적은 결과이고, 단위 테스트(`tests/unit/seed.test.ts`의 "샌드박스 12건이 tasks/T001.md 배정

## 시연용 배송사 데이터 (`carrier-events.json`, v2.5)

`carrier-events.json`은 **배송사 추적 이벤트**다 — PayPal에서 받아 온 데이터가 아니라 우리가
시연을 위해 적은 데이터이고, 그래서 모든 줄에 `isDemo: true`가 붙고 화면은 늘 **'Demo data'
배지**를 붙인다 (SPEC 10장의 "시연용 데이터" ①). 세 군데에 쓰인다: ① 분류 입력
(`ClassifyInput.trackingEvents`)에 이벤트의 `text`가 그대로 들어간다 ② 서연 화면(S5)의 **"배송사
정보 반영 후"** — O01의 통관 보류 줄이 A1(추적 없는 미수령)에서 A2(통관 보류)로 넘어가는 근거다
(SPEC 2장. 실제 분쟁 D2는 추적번호가 없는 샌드박스 주문 O13에 걸려 있고, 시드의 D2는 O01을
가리킨다) ③ buyer_m의 **배송 완료 기록** — O08의 `delivered` 줄이 "배송 완료 기록 + 이전 미수령
분쟁 2회" F1(악용 의심) 판정의 배송 쪽 근거다 (SPEC 4장 규칙 2).

| 주문 | 흐름 | 비고 |
|---|---|---|
| O01 (서연, 주문일 10-17, D2) | `shipped` 10-18 → `in_transit` 10-21 → `customs_hold` **10-30** | 통관 보류 글은 원문 S5 예시 그대로 `Customs hold – recipient customs ID missing` (가운데 줄표는 en dash). **배송 완료가 없다** |
| O08 (buyer_m, 주문일 10-16, D3) | `shipped` 10-17 → `in_transit` 10-19 → `out_for_delivery` 10-21 → `delivered` **10-22** | 배송 완료가 10/28 문의 "Same problem again - the package is not here."보다 앞이라 "배송 완료 기록이 뜬 뒤에 못 받았다고 했다"는 흐름이 성립한다 |

그 밖의 주문에는 이벤트를 넣지 않는다 (필요한 최소). 글은 배송사가 쓸 법한 짧은 영어 한 줄이고
이름·이메일·주소·개인통관고유부호 값은 넣지 않는다. 주문마다 날짜 오름차순이고, 이벤트 날짜는
그 주문일 이후·시연 시점(2026-11-10) 이전이다 (`schemas.ts`의 `carrierEventProblems`가 생성
때 확인한다). 화면·다른 레인은 `seed/index.ts`의 `seedCarrierEvents`나 `carrierEventsFor(orderId)`
(날짜순, 없으면 빈 배열)로 읽는다 — 어느 쪽도 판정·계산을 하지 않는다.

## 주문일 (`SeedOrder.date`, v2.2)

창은 시연 시점 2026-11-10 (SPEC 7장) 기준 90일 **2026-08-12 ~ 2026-11-10**(양끝 포함)이고,
`schemas.ts`의 `ORDER_DATE_WINDOW`가 생성과 검증 양쪽의 기준값이다.

- **샌드박스 12건 + 원문 6-2 구매자 10건(SO001~SO010)**: `data.ts`의 draft에 날짜를 손으로
  적었다. 이야기와 맞춘다 — 서연의 O01은 11/09 "벌써 3주째" 문의보다 3주 이상 앞(10-17),
  진행 중 분쟁(D1·D2·D3)의 주문은 최근 4주 안, 종결 분쟁(D4~D9)의 주문은 창의 앞쪽·중간,
  "배송이 안 온다"는 문의(A1·A2·F1 신호)를 한 구매자는 그 문의보다 먼저 주문했다.
- **자동 생성 주문 192건**: `창 시작 + (i × 33) mod 91`일. 33과 91이 서로소라 창의 91일을 한
  바퀴 다 돌고 다시 시작한다 → 날짜마다 2~3건으로 고르게 퍼진다 (한 날짜 최대 5건). 그 구매자가
  배송 문의를 했는데 규칙 날짜가 문의일 이후면 문의일 3주 전으로 당긴다 (현재 2건).
- 월별 건수: 2026-08 46 · 09 73 · 10 74 · 11 21 (8월은 12일부터, 11월은 10일까지라 적다).
- 종결 분쟁이 걸린 주문일: O09 08-20 · SO002 08-25 · SO003 09-02 · SO004 09-10 · O10 09-14 ·
  SO006 09-18. 진행 중: O02 10-15 · O08 10-16 · O01 10-17.

샌드박스 12건이 바뀌어도 전체 합계는 그대로다: 나머지 202건은 상품별(62·48·33·71)·국가별·추적
할당량에서 남은 몫을 자동으로 채우므로, 샌드박스 쪽 상품·추적 배정이 바뀌면 자동 생성 주문의
상품·추적만 그만큼 반대로 움직인다.
